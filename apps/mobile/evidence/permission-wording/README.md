# Permission wording — Reproduction R1

The owner screenshot records the real defect: the human turn starter is the request subject, commands say “use”, and the Android body still says “wants” after Always.

## Automated reproduction and demonstration

`apps/server/src/grant-card-phrase.test.ts` exercises the production server phrase with different human and agent identities. The original implementation failed the nine per-kind assertions. The fixed implementation passes all ten cases, including unchanged connection-request wording.

`apps/server/src/notification-actions.test.ts` runs the production mobile action handler through its presentation dependency for Android and iOS and Once, Always, and No. The original implementation failed all six outcome-body assertions. All six now pass. Android retains the original notification identifier; iOS uses the existing `#done` identifier. Success removes the action category and subtitle. These portable mobile regressions run in server CI without loading Expo.

The existing `integration/grants-approvals-3.test.ts` also passes the complete daemon grant loop, including a coalesced command card with the agent subject and “run” for both commands. Root typecheck, the remaining grant-copy tests, and the system-line and producer tests pass.

## Android screenshots and limits

Captured on the authorized, already-running Android emulator. The installed Beeline APK was a release build and could not load the changed JS directly. Expo Go also lacks the required native notification channel provider. The closest stand-in is an isolated native fixture (`app.usebeeline.permissionproof`) built with the installed Expo/RN dependencies, the production mobile handler and Expo's native scheduling/presentation API. Its server decision dependency succeeds locally; no real grant is approved.

The request body is generated by the changed server `grantCardPhrase`. The baseline handler comes from the pre-change Git version. The proof script invokes each handler with the notification response fields, then feeds its returned identifier/body/subtitle into the repository's `AndroidPushReplay.java`, using the fixture APK's actual Expo/Firebase notification models and native presenter. All outcomes reuse the original tag; the decided accessibility dumps must contain the expected body and no “wants” text.

The fixture's shade callbacks did not arrive, and its JavaScript scheduling call resolved without visibly replacing the request. The native replay is therefore the closest successful stand-in. These captures prove native rendering of the production handler's output in the same slot, not end-to-end action dispatch, JavaScript scheduling, or FCM transport. Those paths are unchanged. This limitation is retained for review rather than treated as a passing real-device tap.
- `before-request.png`: the baseline request names lunchbox and says “use”.
- `before-decided.png`: baseline Always retains the request body and shows “Always allowed”.
- `after-request.png`: “Jellybean wants to run node scripts/live-a.mjs”.
- `after-always.png` and `after-once.png`: the same notification slot shows “Accepted”.
- `after-deny.png`: the same slot shows “Denied”.

`card-bone.png` and `card-obsidian.png` are the actual, unchanged `GrantRequestCard` rendered by an isolated Expo web fixture in Chrome on the same Android emulator, using the production themes. They demonstrate the existing agent-first title and per-kind wording; they are not screenshots of a signed-in native Room. iOS proof is the six-platform/action regression matrix above, not an iOS device capture.

The fixture source is supplied with the handover as `permission-proof-fixture.zip`; generated Android output and dependency copies are excluded.
