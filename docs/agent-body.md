# Body agent invariants

- **A closed connection is the only reconnect trigger.** `live-link.ts` owns the machine socket and uses OS TCP keepalive; it has only connected/disconnected states. Free-agent VMGenID resume events terminate the restored attempt through that same owner; its actual close opens the successor (`free-agent-resume.ts`, `machine-link-recovery.test.ts`). Failed upgrades preserve connection demand and finish on response `close`, including truncated bodies; only a complete explicit update-required response hands off to the updater. Discovery failures, refused requests, turn deadlines, successful initial snapshots and local progress never replace it. A failed pushed queue read closes the connection through `daemon-api-client.ts`, and the next registration reads the queue again. Coverage: `helper-operation-socket.test.ts`, `machine-link-recovery.test.ts`, `live-link-handshake.test.ts`, `machine-link-rollout.test.ts`.

- **One queue per agent; the server keeps it.** `queueMessage` (`agent-command.ts`) is the single conversational entry for a chat tag, DM, order, report or wake. It checks current membership once and appends one `agent_commands` item with its source place and return address. The helper receives the agent's whole list of undone items (`commands` frame, `commandProtocol: 2`) after registration and on every change. An item is done only when its answer is posted to the return address (`postRoomMessage`), a report is posted there, background work ends with nothing to say, the harness ends without a public answer, or Stop cancels it. A duplicate answer after a crash is acceptable; a harness ending without an answer completes quietly. `answerQueuedMessage` owns the exit: the frozen return address, membership and Stop, publication, then completion. A mid-turn reply records its receipt; closing text becomes activity if that reply already exists. The queued message snapshot supplies delivery without optional context joins. Walls: [walls.md](walls.md).
- **The helper hands items to the agent's live session.** `agent-runner.ts` keeps one `PlaceSession` (`place-session.ts`) per place (Room, DM or corner), the same code for all three, and delivers that place's items to the same conversation; a reconnect backlog arrives as one prompt per place with a private stale-work note measured from the last connection release, and only the newest run of each schedule is shown. All covered items stay pending until the combined answer reaches their recorded return addresses. A new item for a busy place goes in as follow-up input when steering is supported, or remains queued as its next input. The answer is written to disk (`answer-store.ts`) before it is posted; a reconnect or a restarted helper posts the stored answer again and never asks the agent again. If the harness ends without a public answer or fails while answering, the helper stores an empty closing receipt and the server completes the item without a chat message or report. An unstartable harness leaves the item queued with only the offline connection notice. Usage, traces, tool history and model-file cleanup run after the answer is stored and never hold it.
- **Nothing before delivery can stop it.** Cold sessions use cached model/persona/reviewer settings or disclose their agent defaults. Optional configuration, member, repository, corner and grant reads start after prompt delivery; `SessionResources` exposes ready values, pending reads and errors through `read(facet:session)`. Optional skills/setup run only when the agent asks with `read(facet:session,name:prepare)`. Registry routes join `app_tool(app:"registry-mcp:<serverName>")` when loaded; path/device grants are read by `run_granted_command` for its tool sandbox, without replacing the live session. The agent's copy of the code, its index and dependency installs are the `workspace` tool and the agent's own shell, run inside its session. GitHub tokens are fetched when git or gh runs. If the sandbox cannot start, the session runs with writes refused outside its own folder and the agent is told so. Only a harness that cannot start at all leaves the item waiting.
- **The helper is a thin client:** `machine-helper.ts` hosts agents; `agent-runtime.ts` runs one `AgentRunner` per agent, every operation through `DaemonApiClient`. Sessions share `agent-home.ts`, `acp.ts`, model selection, persona delivery, bwrap spawning and the agent MCP (`read-only-mcp.ts`).
- **Agent processes have one owner and no capacity ceiling.** `place-session.ts` starts a harness for a place's first item and keeps it running; one stay-warm countdown (`AgentRunner.armIdle`) stops an idle one, and native resume restores its conversation on the next item. `HostPlaces` (`agent-process.ts`) tells storage sweeps which places are live; sweeps skip them and never make a session wait. Only exact tagged Stop is server control; other tagged commands arrive as agent input. Architecture's `helper.agent-process` rule owns ACP start/stop calls.
- **Daemon operation dispatch has one owner.** Every runtime operation uses `AgentChannel.requestOperation`; callers cannot acquire transport capabilities (`scripts/router-boundaries.mjs`, mutation tests in `router-boundaries.test.mjs`). The private HTTP adapter serves explicit one-shot repository credential readers only. Conversational tools use the private session bridge and the already bound native agent connection. Server HTTP ingress remains for installed older helpers and optional tools, sharing `DaemonService` authorization. Operations run independently of the serial intake queue so external work cannot block Stop/subscriptions. Coverage: `helper-operation-socket.test.ts`, `daemon-live.test.ts`.

- **One machine handshake, all agents and capabilities.** `machine-helper.ts` hosts agents in-process; `machine-link.ts` registers them together, and each agent asks for its queue once per registration (`subscribe-queue`), then receives pushes. The native manager restarts an exited helper; there is no systemd watchdog or application heartbeat/pong timer. Server machine output and login/version changes belong to `machine-connection.ts`. Helper timers are banned except the stay-warm countdown in `AgentRunner.armIdle` and the single cancellable update handoff timeout in `ReleaseTransaction.begin`. Proofs: `scripts/machine-connection-boundaries.test.mjs` plants forbidden reconnect/timer paths; `machine-connection-drop.test.ts` drops the socket repeatedly across 24 answers.

- **Emulators belong to the host.** Agents request host access with `request_grant(kind:host, target:"127.0.0.1:5037", reason, purpose)`; only the host owner's signed Allow authorizes use of an already running emulator. Calling the tool again reads live grant authority and the host adb device list, confirms each transport, returns its address and serial, or tells the agent to report unavailable/refused without using an emulator. SDK platform-tools discovery in `buildAgentEnv` happens before the private HOME overlay; this exposes the client without authorizing emulator use. A host approval needs no sandbox remount and the next `request_grant` reads current authority in the same session. The helper never creates, boots, manages or stops emulators, starts adb servers, repairs KVM access, or provisions AVDs. `machine-control.ts` owns the read-only host probe; `read-only-mcp.ts` owns the grant tool. Regression: `host-emulator.test.ts`; CI guard: `scripts/check-no-emulator-start.mjs`.

- **Installed agent programs are authoritative.** Connect lists all supported harnesses and checks the selected program before probing. An unavailable program leaves its requests queued and publishes only the offline connection notice. Claude/Codex/Pi adapters receive the user program paths; adapter updates follow npm latest with a 24-hour publish-age delay, side-by-side installs and the shared session-start check before atomic adoption; optional bundled harness binaries remain omitted. The daily feedback-triage adapter check uses no login or credential. Commands, overrides and proof: [installed agent programs](agent-programs.md).

Handoff tools deliver reports, posts and orders without inspecting their prose for private paths. Upload deliverable files with `post_artifact` and cite their attachment filenames; required brief files still travel through the target brief. Tracked relative source citations remain valid.

### Android device proof from a corner

Use this route in the current corner; no session restart or `adb connect` is needed:

1. Call `request_grant(action:"request", kind:"host", target:"127.0.0.1:5037", reason:"Android device proof", purpose:"Check the Android change on an existing host emulator")`.
2. If permission is pending, end the turn and wait for the host owner's Allow. On the approval wake, repeat that call. Refused permission requires the host owner's decision before retrying.
3. The tool enumerates the existing host server, then confirms each listed emulator with `host-serial:<serial>:get-state`. Run one returned `adb -H 127.0.0.1 -P 5037 -s <serial> get-state` command; expect `device`. Keep the same host, port and serial options on every proof command, including `shell`, `install` and `exec-out`.
4. If a serial disappears between discovery and use, repeat the grant call for a fresh address. Never keep using a serial copied from an earlier turn. If none is available, ask the host owner to make a running emulator available, then retry the grant call. The agent never starts an emulator or adb server.

An Allow authorizes access; it does not reserve a device or keep it alive. The grant result is a current connection check, not a lease. Missing `adb` is a host SDK setup problem: ask the host owner to install platform-tools or repair the helper PATH, then retry the same route.

## Lifecycle, commands and model selection

Paths and commands below are relative to the repository root. Read these invariants before editing this area; named code and tests hold implementation detail.

### Updates and startup

- **A helper update never waits for agents.** `ReleaseTransaction` (`managed-update.ts`) hands off as soon as a verified release is prepared; queued and in-flight items stay on the server and are answered by the next helper. Preparation and handoff each have a three-minute cancellable deadline (`managed-update.startup.test.ts`).
- **ACP scopes bind to the helper's lifetime without ordering after its readiness.** `AcpResourceScope` (`apps/body/src/acp-resource-scope.ts`) keeps `BindsTo` without `After` (`acp-resource-scope.startup.test.ts`).
- **Native conversation memory survives helper restarts.** A place session loads its harness conversation from private `agent-home/warm-transcript.json` when the model, persona, command and folder match; otherwise it starts cold.

### Tagged control commands

- **Exact tagged Stop is server control.** `queueMessage` cancels the addressed pending items. Other tagged commands, including restart/status/help/login, are ordinary agent inputs and cannot be dropped by a separate control router.

### Model catalog

- **A model picker is a live account verdict; readiness never waits for a harness.** `apps/body/src/model-catalog.ts` offers models proved through the live setter. Sessions use verified launch arguments or the advertised/default model and disclose a requested model that was not selected; startup does not call the optional model setter. Catalog publication runs independently of delivery. No startup model request or diagnostic write may gate readiness (`agent-runtime.startup.test.ts`). Transient provider failures remain hiccups rather than model verdicts (`isTransientProviderText`, `isAuthShapedFault`).

- **Agent tool schemas stay compact.** `minimal-tool-surface.ts` declares the canonical ordinary tools; `read-only-mcp.ts` maps post/order/report directly to the native conversational owner; optional resource tools validate their advertised schemas. Procedure reads accept the advertised `slug` or `name`; message reads default to newest first, with explicit `from:oldest` retained. `no_reply_needed` acknowledges context without completing an unanswered owed request; it finishes background work. Workflow, wallet, browser-share and avatar schemas are discovered through `app_tool` first-party routes; no mid-session tool-list refresh is assumed. Pi exposes each optional server as `<server>__mcp`; discovery and calls run only when the agent requests them. `PlaceSession` owns the scratch sandbox and private home. If its configured home cannot be created, a fresh private folder and an agent diagnostic preserve delivery. An offline Codex Room keeps scratch IO even with a native shell (`roomNativeIoProven` in `harness-capabilities.ts`). `revise_corner(action:brief)` accepts a complete brief projection copied from `read`; Body discards returned metadata and the server resolves approval and files again. Schedule updates/deletes still require a turn started by a human Workspace admin of the schedule’s Room; scheduled wakes are refused. Schedule prompts are bounded to 2,000 UTF-16 code units without limiting conversational report text. Proof: `node --import tsx scripts/prove-tool-description-contract.mjs` after building Body and server (R1/R2). Measure exact descriptors with `npm run measure:agent-tools -- <output-dir>`; authority and privacy regressions live in `minimal-tool-surface.test.ts`, `commander.integration.test.ts` and `corner-lifecycle.test.ts`.

Run `node --import tsx scripts/prove-agent-tool-traps.mjs` after building Body and server for the isolated message-read, procedure-name, owed-tag, schedule-title, silent-feedback and Squire-silence proof (Reproduction 7).

Reviewer sessions read current checks, the brief and git head through their tools; startup does not fetch them. A stored pending lifecycle cannot override live passing checks; a mismatched checkout or unavailable provider read gives an unverified-target instruction, never a claim that GitHub checks failed. Coverage: `agent-runner.test.ts`, Reproduction `stale-green`.
