# Body agent invariants

- **A closed connection is the only reconnect trigger.** `live-link.ts` owns the machine socket and uses OS TCP keepalive; it has only connected/disconnected states. Free-agent VMGenID resume events terminate the restored attempt through that same owner; its actual close opens the successor (`free-agent-resume.ts`, `machine-link-recovery.test.ts`). Failed upgrades preserve connection demand and finish on response `close`, including truncated bodies; only a complete explicit update-required response hands off to the updater. Discovery failures, refused requests, turn deadlines, successful initial snapshots and local progress never replace it. A failed pushed queue read closes the connection through `daemon-api-client.ts`, and the next registration reads the queue again. Coverage: `helper-operation-socket.test.ts`, `machine-link-recovery.test.ts`, `live-link-handshake.test.ts`, `machine-link-rollout.test.ts`.

- **One queue per agent; the server keeps it.** `queueMessage` (`agent-command.ts`) is the single conversational entry for a chat tag, DM, order, report or wake. It checks current membership once and appends one `agent_commands` item with its source place and return address. The helper receives the agent's whole list of undone items (`commands` frame, `commandProtocol: 2`) after registration and on every change. An item is done only when its answer is posted to the return address (`postRoomMessage`), a report is posted there, background work ends with nothing to say, an automatic idle episode becomes obsolete, or Stop cancels it. An empty harness result never completes an unanswered human request. `answerQueuedMessage` owns the exit: the frozen return address, membership and Stop, publication, then completion. A reply to another request leaves the current turn’s final eligible to publish. If the current request already received its reply in a different place, the final posts in the turn’s place. After a stored, visible reply to the current request in the turn’s own place, the harness-ended final is not posted again; its text and steps go to the turn’s activity (`recordSuppressedFinal`, `answer-activity.ts`). Finals with files, explicit posts and review verdicts (`keepFinal`) still post. The queued message snapshot supplies delivery without optional context joins. Queue insertion freezes thread brief and membership changes with the command (`attachQueuedConversation`, `agent-command-context.ts`). Person tags can read earlier messages on demand with `read(facet:messages)`. Other wakes also get messages since the previous command. For those wakes a fresh `PlaceSession` gets the bounded recent window (`conversationWindow`) once, and external wakes get the delta after the institutional snapshot. Walls: [walls.md](walls.md).
- **The helper hands items to the agent's live session.** `agent-runner.ts` keeps one `PlaceSession` (`place-session.ts`) per place (Room, DM or corner), the same code for all three, and delivers that place's items to the same conversation; a reconnect backlog arrives as one prompt per place with a private stale-work note measured from the last connection release, and only the newest run of each schedule is shown. All covered items stay pending until the combined answer reaches their recorded return addresses. A new item for a busy place remains queued for its next prompt; all waiting items in that place arrive together. Steering acceptance is not an answer receipt. The answer is written to disk (`answer-store.ts`) before it is posted; a reconnect or a restarted helper retries it with its original invocation identity. A successful empty harness turn can finish background items and scheduled wakes without posting. The helper saves the successful silence with the closing receipt so retries can deliver it after a disconnect. Scheduled wakes stay pending for a later queue delivery if the harness fails to start or run. Unanswered human requests on personal helpers also stay pending. An unanswered hosted human request ends through the existing visible failure line when its harness returns no text. Tool activity and pre-tool progress prose are not public replies. Automatic attention reports can use `no_reply_needed`; idle reports retain their episode and are retired when that episode is no longer current. Completed thread tool steps publish through `LiveTurnSteps` during the prompt and are omitted from the final history once saved. Usage and traces are recorded after the answer is stored. Harness-reported token metrics accompany `postAgentTurnReceipt` through `mergeHarnessTurnMetrics`; unavailable metrics stay absent.
- **The shared command read supplies active threads before delivery.** The helper appends existing local checkout paths when it renders the list. Person tags can read the list on demand. Before each delivery, `SessionResources` selects the latest received command snapshot or completed optional thread refresh, including for waiting and batched commands; superseded refreshes cannot overwrite a newer refresh. Optional thread reads run during and after turns without delaying delivery. Cold sessions use cached model/persona/reviewer settings or disclose their agent defaults. Optional configuration, member, repository, restore and grant reads start after prompt delivery; `SessionResources` exposes ready values, pending reads and errors through `read(facet:session)`. The selected harness's release-owned Beeline skills are installed best effort before the harness starts, including in a recovery home, because a harness discovers skills only at process start. Startup preserves existing operator skill entries without discovering or copying operator shares; installation failures warn without blocking delivery or replacing the home. Optional setup runs when the agent asks with `read(facet:session,name:prepare)`, which refreshes the full skills tree including operator shares and also runs the `workspace` checkout preparation. For repository-backed places, setup reports ready only after the checkout exists at the current origin base (a thread checkout with no commits of its own fast-forwards to it) and, inside the session's OS sandbox, the repository's `corner:prepare` script ran, or else `npm ci` and its `build` script (`workspace-checkout.ts`); a failed step fails setup with its output, and a host without the sandbox is told the checkout is not ready. Places without a repository return that fact without creating a checkout. The agent can also prepare or refresh the checkout directly with `workspace`. Existing corner storage reconciles `origin` to the server-provided remote before fetching (`agent-corner-checkout.ts`). New per-agent checkouts start from Git refs without importing the old shared checkout; an unfinished legacy import marker blocks reuse rather than resuming the copy. Registry routes join `app_tool(app:"registry-mcp:<serverName>")` when loaded; the CodeGraph MCP server (`codegraphMcpServer`) and operator-imported host MCP routes (`grantedHostRouteWires`, each call gated by the resource façade) mount with the session; path/device grants are read by `run_granted_command` for its tool sandbox, without replacing the live session. The agent's copy of the code, its index and dependency installs are the `workspace` tool and the agent's own shell, run inside its session. Once a thread checkout exists, each turn first brings it onto the remote feature branch (`corner-branch-sync.ts`: fast-forward or rebase, uncommitted work preserved); a failed refresh still delivers, with one line telling the agent. Received images are delivered inline when the harness supports image prompts, within the attachment byte limit (`attachment-delivery.ts`); branch refresh and image delivery precede the prompt. GitHub tokens are fetched when git or gh runs. If the sandbox cannot start, the session runs with writes refused outside its own folder and the agent is told so. A hosted starter harness that cannot start for a human request ends it as a visible failed turn with the actual reason.
- **The helper is a thin client:** `machine-helper.ts` hosts agents; `agent-runtime.ts` runs one `AgentRunner` per agent, every operation through `DaemonApiClient`. Sessions share `agent-home.ts`, `acp.ts`, model selection, persona delivery, bwrap spawning and the agent MCP (`read-only-mcp.ts`).
- **Agent processes have one owner and no capacity ceiling.** `place-session.ts` starts a harness for a place's first item and keeps it running; one stay-warm countdown (`AgentRunner.armIdle`) stops an idle one, and native resume restores its conversation on the next item. `HostPlaces` (`agent-process.ts`) tells storage sweeps which places are live; sweeps skip them and never make a session wait. Architecture's `helper.agent-process` rule owns ACP start/stop calls.
- **Daemon operation dispatch has one owner.** Every runtime operation uses `AgentChannel.requestOperation`; callers cannot acquire transport capabilities (`packages/scripts/router-boundaries.mjs`, mutation tests in `router-boundaries.test.mjs`). The private HTTP adapter serves explicit one-shot repository credential readers only. Conversational tools use the private session bridge and the already bound native agent connection. Server HTTP ingress remains for installed older helpers and optional tools, sharing `DaemonService` authorization. Operations run independently of the serial intake queue so external work cannot block Stop/subscriptions. Coverage: `helper-operation-socket.test.ts`, `daemon-live.test.ts`.

- **One machine handshake, all agents and capabilities.** `machine-helper.ts` hosts agents in-process; `machine-link.ts` registers them together, and each agent asks for its queue once per registration (`subscribe-queue`), then receives pushes. The native manager restarts an exited helper; there is no systemd watchdog or application heartbeat/pong timer. Server machine output and login/version changes belong to `machine-connection.ts`. Machine liveness timers are banned. Wait ownership and its migration ratchet are defined in the [helper wait boundary](architecture/README.md#architecture-invariants). Proofs: `packages/scripts/machine-connection-boundaries.test.mjs` plants forbidden reconnect/timer paths; `machine-connection-drop.test.ts` drops the socket repeatedly across 24 answers.

- **One shared emulator belongs to the host.** `request_grant(kind:host, target:"127.0.0.1:5037", reason, purpose)` discovers an already running emulator without a permission card, regardless of YOLO. It confirms each transport and returns its current address and serial, or reports unavailable. SDK platform-tools discovery in `buildAgentEnv` happens before the private HOME overlay. The helper never creates, boots, manages or stops emulators, starts adb servers, repairs KVM access, or provisions AVDs. `machine-control.ts` owns the read-only host probe; `read-only-mcp.ts` owns the discovery tool. Regression: `host-emulator.test.ts`; CI guard: `packages/scripts/check-no-emulator-start.mjs`.

- **Installed agent programs are authoritative.** Connect lists all supported harnesses and checks the selected program before probing. An unavailable personal program leaves its requests queued and publishes the offline connection notice. Claude/Codex/Pi adapters receive the user program paths; adapter updates follow npm latest with a 24-hour publish-age delay, side-by-side installs and the shared session-start check before atomic adoption; optional bundled harness binaries remain omitted. The daily feedback-triage adapter check uses no login or credential. Commands, overrides and proof: [installed agent programs](agent-programs.md).

- **One owner per provider login.** The machine helper runs one CLIProxyAPI child (`cliproxy.ts`: latest release, checked against the checksum published with it, bound to `127.0.0.1`, config and logins under the masked `~/.config/beeline/cliproxy`). It alone refreshes the Claude, ChatGPT and xAI logins. Claude Code, Codex and Grok sessions reach it with only the local inference key, as do unkeyed Pi/OpenCode subscription providers and Goose's unkeyed Anthropic/OpenAI providers; their homes hold no upstream refresh tokens. The helper dispatches `/login` for the current server-selected provider: Codex and xAI use proxy device login; Claude's exchanged login is handed to the proxy once. Plan reads give quota-axi an access-token-only copy; successful sign-in invalidates the shared provider quota cache and older in-flight reads. User sign-in and migration steps live in the [README](../README.md#get-started). Cursor keeps native login links; Pi and OpenCode keep private static API-key copies; Goose uses private config/secrets copies. See the [sandbox policy](approval-matrix.md). Proof: `cliproxy.test.ts`, `cliproxy-routes.test.ts`, `harness-login-mounts.test.ts`, `agent-sign-in.test.ts`, `place-session.test.ts` and `workspace-checkout.sandbox.test.ts`.

Handoff tools deliver reports, posts and orders without inspecting their prose for private paths. Upload deliverable files with `post_artifact` and cite their attachment filenames; required brief files still travel through the target brief. Tracked relative source citations remain valid.

### Android device proof from a corner

Use this route in the current corner; no session restart or `adb connect` is needed:

1. Call `request_grant(action:"request", kind:"host", target:"127.0.0.1:5037", reason:"Android device proof", purpose:"Check the Android change on an existing host emulator")`.
2. No approval is required. If no shared emulator is available, report that result; the host owner supplies the running emulator.
3. The tool enumerates the existing host server, then confirms each listed emulator with `host-serial:<serial>:get-state`. Run one returned `adb -H 127.0.0.1 -P 5037 -s <serial> get-state` command; expect `device`. Keep the same host, port and serial options on every proof command, including `shell`, `install` and `exec-out`.
4. If a serial disappears between discovery and use, repeat the grant call for a fresh address. Never keep using a serial copied from an earlier turn. If none is available, ask the host owner to make a running emulator available, then retry the grant call. The agent never starts an emulator or adb server.

Discovery does not reserve a device or keep it alive. The grant result is a current connection check, not a lease. Missing `adb` is a host SDK setup problem: ask the host owner to install platform-tools or repair the helper PATH, then retry the same route.

## Lifecycle, commands and model selection

Paths and commands below are relative to the repository root. Read these invariants before editing this area; named code and tests hold implementation detail.

### Updates and startup

- **Pi rules live in its system slot.** `installPiSystemPrompt` (`pi-session-instructions.ts`) writes the session rules to `PI_CODING_AGENT_DIR/SYSTEM.md` before `session/new`, replacing Pi's default system prompt. Turn messages carry no rule prefix, including after compaction. Coverage: `pi-session-instructions.test.ts`, `pi-chat-turn.test.ts`.
- **A helper update never waits for agents.** See the [CLI bundle runbook](cli-bundle-channel.md#recovery-and-the-first-update-from-an-old-release) for update completion and failure behavior (`managed-update.startup.test.ts`).
- **ACP scopes bind to the helper's lifetime without ordering after its readiness.** `AcpResourceScope` (`apps/body/src/acp-resource-scope.ts`) keeps `BindsTo` without `After` (`acp-resource-scope.startup.test.ts`).
- **Native conversation memory survives helper restarts.** A place session loads its harness conversation from private `agent-home/warm-transcript.json` when the model, persona, command and folder match; otherwise it starts cold.

### Tagged control commands

- **Exact tagged Stop is server control.** `queueMessage` cancels the addressed pending items; the helper then ends the session's process tree (harness, MCP servers and tools it started) and that place's running granted commands (`PlaceSession.cancel`), even when the harness ignores `session/cancel`, and the next item starts fresh. Exact tagged Restart records a completed reset request in the message transaction. The helper receives the latest reset with its queue snapshot, detaches the old session, cancels its grants, and hands teardown to the process owner while a fresh session takes the still-owed input. The server records confirmation when that fresh session starts its turn.

### Model catalog

- **A model picker is a live account verdict; readiness never waits for a harness.** `apps/body/src/model-catalog.ts` offers models proved through the live setter. Sessions use verified launch arguments or the advertised/default model, then reconcile a differing chosen model or independently changed effort/Fast Mode against the fresh harness catalog. Effort and Fast Mode alone never hold delivery; a model change holds the first prompt until the harness answers its setter (owner-approved 22 Nov 2026), so a commanded switch takes effect on that turn. Only a chosen model absent from that catalog is disclosed as unavailable. Each session reports the model it actually runs, and why a chosen model was not applied, through `postAgentRunningModel` after its first prompt; member labels and the agent sheet name that running model and show any mismatch with the stored choice (`running-model.integration.test.ts`). Each queue item carries the owner's model, effort and Fast Mode as the server read them with the item; a live session running another choice starts fresh before answering, so no turn waits for a configuration read. An owner's configuration change also retires the place's session and starts a fresh configuration read, including for a place first seen after the change. When the read names a newer selection than a live session started with, `session-running-model.ts` switches that session's model through the same unawaited setter and reports the result (`place-session.test.ts`). Catalog publication runs independently of delivery. No startup model request or diagnostic write may gate readiness (`agent-runtime.startup.test.ts`). Transient provider failures remain hiccups rather than model verdicts (`isTransientProviderText`, `isAuthShapedFault`).

- **Agent tool schemas stay compact.** `minimal-tool-surface.ts` declares the canonical ordinary tools; `read-only-mcp.ts` maps post/order/report directly to the native conversational owner; optional resource tools validate their advertised schemas. Procedure reads accept the advertised `slug` or `name`; message reads default to newest first, with explicit `from:oldest` retained. `no_reply_needed` acknowledges context without completing an unanswered owed request; it finishes background work. Workflow, wallet, browser-share and avatar schemas are discovered through `app_tool` first-party routes; no mid-session tool-list refresh is assumed. Pi exposes each optional server as `<server>__mcp`; discovery and calls run only when the agent requests them. `PlaceSession` owns the scratch sandbox and private home. If its configured home cannot be created, a fresh private folder and an agent diagnostic preserve delivery. An offline Codex Room keeps scratch IO even with a native shell (`roomNativeIoProven` in `harness-capabilities.ts`). `revise_thread(action:brief)` accepts a complete brief projection copied from `read`; Body discards returned metadata and the server resolves approval and files again. Schedule updates/deletes still require a turn started by a human Workspace admin of the schedule’s Room; scheduled wakes are refused. Schedule prompts are bounded to 2,000 UTF-16 code units without limiting conversational report text. Proof: `node --import tsx packages/scripts/prove-tool-description-contract.mjs` after building Body and server (R1/R2). Measure exact descriptors with `npm run measure:agent-tools -- <output-dir>`; authority and privacy regressions live in `minimal-tool-surface.test.ts`, `commander.integration.test.ts` and `corner-lifecycle.test.ts`.

Run `node --import tsx packages/scripts/prove-agent-tool-traps.mjs` after building Body and server for the isolated message-read, procedure-name, owed-tag, schedule-title, silent-feedback and Squire-silence proof (Reproduction 7).

Reviewer sessions receive the queue-time brief with conversation context as described above and verify current checks and git head through their tools; startup does not fetch those verdicts. A stored pending lifecycle cannot override live passing checks; a mismatched checkout or unavailable provider read gives an unverified-target instruction, never a claim that GitHub checks failed. Coverage: `agent-runner.test.ts`, Reproduction `stale-green`.
