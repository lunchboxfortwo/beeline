# Corner work and personal-resource approvals

| Resource                                                                         | Root requester and yolo          | Result                                                                                 |
| -------------------------------------------------------------------------------- | -------------------------------- | -------------------------------------------------------------------------------------- |
| Executing agent’s owner-machine paths, secrets, host commands and imported tools | YOLO off / on                    | Resource owner approval / automatic approval for that owner’s resources                |
| Existing shared host Android emulator (`host`, `127.0.0.1:5037`)                 | Any                              | No approval; discover and confirm an already running device; never start or manage one |
| Another person’s files or tools outside the sandbox                              | Any                              | Ask that resource owner                                                                |
| Wallet                                                                           | Existing requester and yolo rule | Unchanged                                                                              |
| Command naming a credential file or an unread script                             | Any                              | Ask a person; script approval remains bound to its bytes                               |
| Agent’s private cache copy                                                       | Any                              | No approval; copy/configure it under private HOME immediately                          |

Bare tools resolved on PATH skip script cards only when their executable and directory trees are owned by another UID, have no group/other write bits, and are not writable by the executing agent. This preserves root-owned system tools, including under sandbox UID mapping. Writable PATH scripts carry the same byte binding as interpreter files. Inline code uses a literal JSON argv command target; interpreter stdin uses a JSON target containing `argv` and `stdin`, and `run_granted_command` supplies that exact `stdin`. Both put their full code on the existing script card, including shell heredocs. A file over the inline card limit can instead carry its immutable GitHub file URL and SHA-256 when the helper verifies those exact bytes at the current corner PR head and the server confirms that head and file against GitHub’s blob identity. The runner checks both the approved SHA-256 and that Git blob identity; uncommitted files and oversized inline code remain refused. Missing stdin bytes are refused. The runner hashes files relative to the execution cwd (following symlinks), again immediately before spawning after asynchronous grant consumption and secret resolution. Changed or unreadable bound files require a new approval; legacy script grants without a byte binding require re-approval, never a first-run hash enrollment. Explicit native executable grants retain their existing behavior. Always requests reuse a live approved grant with matching scope and script bytes; an incompatible newer prefix cannot shadow it. Refusals identify grant IDs and mismatching fields without echoing argv values; expired command grants remain inspectable but never authorize execution. Command grants have no stored cwd or host field: cwd is reported when resolving a script fails or its hash changes, while the executing agent's helper owns the host route. Proof: `node --import tsx packages/scripts/prove-always-script-grants.mjs` after building Body and server (`R-ALWAYS-1`, `R-SCRIPT-1`, isolated phone reads and loopback runner; no production approval).

New agent grant requests require a plain-language `purpose` (1–240 characters), stored with the grant and its card. It says what the agent wants to do and why. Optional `touches` and `capabilities` describe known effects in plain language. Path grants preserve an explicit write capability into the sandbox mounts. Command requests may carry an executable path up to 4096 characters in `touches`; their full argv remains the approved command. These fields do not widen command prefixes or change decision authority. Cards lead with this purpose, show available facts, and keep the full script behind Show script. Older requests retain their existing wording with the script folded. No/Once/Always retain their existing decisions.

Private cache copies are ordinary sandbox files. Configure package-manager or Codex caches under private HOME; no standing grant, activation or next-session remount is needed. The dead shared-asset mount plumbing is removed. Older `shared_asset` tool requests return local setup guidance; older helper requests receive a quiet compatibility receipt without creating a grant row or changing any mount. Stored historical rows remain readable.

Connection installation for the executing agent's own account follows effective YOLO: off asks the resource owner; on records automatic approval, including Squire provisioning. First-party and OAuth routes still use the owner's sign-in card when sign-in is needed. Another person's app account retains its owner decision; its card names the asking agent and the app's display name. Retries reuse matching pending, denied, Once or Always consent for the same agent, Room, requester and active app account; Once is consumed before setup instructions are returned. Automatic installation consent is usable only while effective YOLO is on. Installation consent does not authorize app use or spending. Boot withdraws only asks that current policy makes obsolete; Ask first requests survive restart.

With effective YOLO on, own-owner access creates a quiet receipt when `request_grant` is used and imported-tool calls pass without a card. With YOLO off, request and per-call gates both require current resource-owner approval. New budget and repository grant requests remain retired. The root requester remains recorded for provenance and for the wallet’s separate consent rule. For managed app tools on a wake without a human requester, `executeAppTool` uses the agent owner as requester only for that owner’s connected app. Agent and hidden scheduler/System authors count as nonhuman wakes here. Other people’s apps retain their existing requester and grant checks; wallet and Squire gates are unchanged. Coverage: `app-connections.integration.test.ts` (`wake-app`).

The isolated checkout and shell of a corner belong to that corner. Host paths outside it, devices, secrets, host commands and MCP routes are personal resources owned by the helper's owner. Any remaining personal-resource cards and automatic access receipts live in the owner's private @System DM; Workspace administrators cannot decide them or read their grant details through an agent profile.

`DaemonService.grantRequester` and institutional resource authority share `apps/server/src/resource-requester.ts`. A human-message root retains its original requester. An agent-originated order uses the issuing root agent's human owner; nested delegations retain the first root, even when an intervening or executing agent belongs to someone else. Agent ownership chains stop at the first human and terminate safely on cycles. Message-backed agent orders, verified source-less `order` roots with an agent author, and source-less `mcp_call` roots use this rule. An MCP root identifies its issuer through the stored `agent_id`; an order root uses its stored private payload author. No delegate payload or executing-agent owner supplies fallback provenance.

A command-only root must still have no source message or parent, and its id must equal both its own and the active command's `root_command_id` and `root_source_message_id`. Existing System-authored automatic orders and idle reports retain their strict root/payload checks and System requester. Unverified roots are refused; no synthetic message is created. Workflow-run requester resolution still takes precedence for grants and workflow archive.

History and memory searches, memory use reports and shared fact writes, Squire's per-message resource facade, and workflow archive use the resolved requester. Every resource keeps its existing authorization: history still checks the requester, answering agent and output audience; profile memory remains requester-scoped; memory sources, DM restrictions and root source partitions remain; Squire keeps its owner/account and grant gates; workflow archive still requires a human Workspace admin. Another person's agent resolves to that person's owner and gains no access to the executing owner's private history, profile facts or admin authority. Wallet consent and merge authority are unchanged. Coverage: `apps/server/src/agent-order-resources.integration.test.ts`, `command-only requester` cases in `apps/server/src/agent-command.integration.test.ts`, and `apps/server/src/helper-activation.test.ts`.

Optional repository-onboarding setup omits its capability flag and guidance when requester provenance is unavailable; command and membership authority still admit the Room or corner activation. Resource effects, including posting onboarding cards, keep the mandatory requester gate. Regression coverage: `apps/server/src/helper-activation.test.ts`.

Delegations, corner objectives and approval resumes retain the original root. It is provenance, not a second owner for the agent’s tools. Live command grants remain tied to their Room and requester. Automatic outside-resource grants cease authorizing calls when YOLO is disabled or the Workspace becomes public. Their current app ownership is rechecked; wallet retains its separate owner-requester rule. Shared emulator discovery is exempt from approval.

All imported MCP routes, including declarations formerly marked local, and the built-in YouTube tool use a transport facade that authorizes every message, including discovery and harnesses that omit permission callbacks. A refused discovery starts no personal-resource process and reaches no HTTP upstream. Wallet discovery does not consume a Once grant; the server consumes it atomically at the first authorized wallet call, and only that call's correlated response can reach the agent. An app connected through `connect` answers to one `app:<key>` target on every route — its Registry MCP server and any Trusty Squire call that names it — and wallet tools retain the original-requester resource gate before discovery, execution, wallet reads, or spending. Wallet signing delegation and sufficient funds remain required.

Opening a Room or corner, starting or closing a corner turn, and using Beeline's own Room and corner tools require no grant. `MonolithCornerTurnLoop` admits a corner turn without repository or host pre-turn checks. Older helpers still call `authorizeRepositoryCall` and `authorizeHostCall`; the server keeps them as allow-only routes under active turn authority, without creating grants or cards. An imported resource call still meets its own owner-presence and app-route gate when made. Approval does not replace the exact-head reviewer/CI/human-hold merge gate. Host root, operator HOME as a whole, user bus and the agent-wide browser socket directory are not writable ambient mounts in any session, including under YOLO. Threads bind only their checkout, existing-inode Git storage and private state writable. Each place's private harness state stays writable; operator login access follows the [harness login policy](#harness-login-write-exceptions) below. Host path access goes through a live grant and the existing granted-command route; credentials and sibling state stay masked. Only an explicit write grant for the user runtime directory adds the writable user-bus mount and preserves the host PID namespace for bus authentication; read-only grants do not add it. Known Docker sockets remain masked without an explicit path grant. Host sockets and local ports otherwise remain directly reachable: network/IPC confinement is explicitly deferred, so this change does not claim all host effects are brokered.

Coverage: server `integration/grants-approvals*.test.ts` (matrix, private decisions, target scope, delegation/resume, revoked and Once grants, command reuse), `wallet.integration.test.ts`; body `grant-runner.test.ts`, `host-mcp-route.test.ts`, `monolith-corner-turn.test.ts`, Room/corner permission tests; mobile `RoomMessageVariants.test.tsx`.

Server migrations no longer revoke approved or Once grants for missing legacy requester provenance. A one-time data migration (`migrations/owner-approved-grants.ts`, recorded as `owner-approved-grant-restore-v1`) restores only unexpired, still-revoked grants whose ledger records `missing-requester-provenance` and previous status `approved`, whose decider is the agent's current owner, and whose decision timestamp is no later than the policy revocation. It changes only the grant status; the retired policy-upgrade revocation ledger (`agent_grant_policy_revocations`) remains unchanged. Other revocations stay revoked, and later migrations do not repeat the recovery. The storage registry marks this ledger as retired, but its rows must remain for retention review. Pending asks the current rule would never raise (effective-YOLO owner-machine access without a hard stop, obsolete emulator/cache asks, and retired budget or repository asks) are withdrawn by `@system` on boot without waking their turns, so their cards stop offering No/Once/Always. This withdrawal only changes pending grants. Automatic access receipts do not push; a permission ask pushes its full text.

Resource ownership is the helper owner's host/tool inventory; wallet and Squire retain their existing owner-bound account resolution. The agent owner's approval is not permission to route another person's Workbench connection through that helper. Generic imported tools must be provisioned for that helper owner. Filesystem confinement is still the documented hygiene boundary, not a new security sandbox; another owner’s app is refused rather than being treated as this helper’s own connection; that person must connect a route on a helper they own before it can be used. Credential-file and unread-script hard stops remain enforced by the granted-command runner, and payment delegation, funds, and merge/review rules remain independent.

### Harness login write exceptions

Sign-in runs in the helper; private harness state remains writable in both session modes. Operator state is read-only except for these login directories, selected only for the running harness by `harnessLoginWritablePaths` (`agent-home.ts`):

| Harness             | Operator state policy                   | Reason                                                                                                  |
| ------------------- | --------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Claude, Codex, Grok | Native login files masked               | See the [provider login contract](agent-body.md); no writable operator login mount.                     |
| Pi, OpenCode        | Native auth stores masked               | Private homes retain static API-key entries only; see the [provider login contract](agent-body.md).     |
| Goose               | `.config/goose` read-only               | Config and secrets are private copies; the helper saves provider keys.                                  |
| Cursor Agent        | `.cursor` and `.config/cursor` writable | Native login maintains both CLI state and auth; complete login/refresh not proved with narrower mounts. |
| Custom/reference    | No additional known operator store      | Existing explicitly configured harness state remains writable where login behavior is unknown.          |

The proxy store and retired native auth stores stay masked even when absent at sandbox startup, so a later host login cannot expose tokens to an existing session (`bwrap-sandbox.ts`).

The Cursor exception permits changes to non-credential files inside those directories. It is a deliberate sign-in fallback, not a claim of credential-only isolation. No credential file is pinned to a writable single-file mount. A missing Cursor store is skipped until helper sign-in creates it and a new session mounts it. Legacy sessions without a private home retain their configured writable state directories because their login behavior has not been proved safe with narrower mounts. These exceptions do not make the rest of operator HOME writable. Sandbox tests prove mount/write contracts; they do not claim live authentication with every provider.

The allow-only compatibility routes let old and new helpers run through either deploy order. No claim of spending caps is made.

## Post-merge evidence

The original implementation shipped in [PR 1712](https://github.com/Beeline-Work/beeline/pull/1712), merge commit `dd387f2aa`. Post-merge review found gaps in Composio requester provenance, facade authorization, migration recovery, and generated approval copy; the follow-up regressions below preserve those findings as executable evidence.

- The Composio connector these findings covered is retired. `app-connections.integration.test.ts` covers connected-app routing and owner usage attribution; `app-resource-approval.integration.test.ts` covers the effective-YOLO execution and installation consent rules above.
- `resource-mcp-facade.test.ts` proves unauthorized discovery starts no stdio child or HTTP request, discovery preserves a Once grant, and unsolicited child output is not forwarded.
- `grant-policy-upgrade.test.ts` proves repeated migrations preserve owner-approved and Once grants without requester provenance, keep the historical revocation ledger unchanged, and withdraw only superseded pending asks. The real PostgreSQL recovery regression in `migration-steps.test.ts` proves the one-time restoration and its exclusions.
- `agent-grant-tools.test.ts` and the server integration suite verify that `request_grant` copy comes from the server-returned destination and authority for private `@system`, Wallet, and Trusty Squire cards.
- The personal-resource matrix, command-runner, wallet, corner, and Google ownership regressions from the merged change remain the supporting coverage for the broader policy boundary.
