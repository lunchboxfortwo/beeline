# Corner authority and lifecycle invariants

Reports from self-opened corners whose opening parent command has expired recover the retained opening root human message in the same Workspace instead of selecting the worker as its own commander (`agent-queue.postgres.test.ts`). Report wakes whose incoming command has expired may recover only their recorded root human message route in the same Workspace; ordinary membership checks still apply. Native RPC retries retain their message ID; separate explicit posts and orders receive separate IDs. Coverage and incident limits: [report and post delivery proof](report-post-delivery-proof.md) (`RETURN-ADDRESS`, `POST-ID`, `REPLY-ONCE`).

Report review evidence comes from the reporting turn (`createAgentCommand.reportSource`), while its parent retains the commander's incoming order for one-step-up routing. The latest human-approved revised brief selects its author as escalation recipient and its dispatching place as return surface; without one, the opening route applies. Agent-only revisions and conversation messages never transfer command. Explicit orders accepted before handover retain their issuer and original return address, including orders from the incoming commander. Question reads use that committed return Room; forwarding a report is not an answer, and a human answer there clears the lifecycle wait as well as its answered marker (`REVIEW-SILENT-1` in `corner-lifecycle-2.test.ts`). An opener inspecting its own corner escalates through its opening parent command. Later human questions receive ordinary replies in the corner. Repair completion retains the reporting turn's head without inheriting its commander's stale review verdict. A current reviewer report retains its own head; a changed head cannot discard its answer. Merge approvals still require the current head. Coverage: `commander-opening.integration.test.ts`, `commander-order-target.integration.test.ts`, Reproduction `report-commander-refused`.

Queued reports carry source attachments through explicit reports and automatic completions. Carried files follow the recorded return route; identical URLs and media object IDs are collapsed without an optional content-hash lookup. Reports keep their source attachments in the queued message snapshot; optional transcript activity follows publication. Coverage: `commander-recovery.integration.test.ts` (`FILE-HANDOFF`); built HTTP and file-opening proof: `node --import tsx scripts/prove-report-files.mjs` after building the server.

Explicit orders to the sending agent queue a new request at the addressed chat or corner. Public self-output does not target its author, and automatic brief-revision notifications exclude the revising agent instead of manufacturing completed work. Every actual incoming order, corner-opening assignment and workflow assignment remains queued until answered or stopped. Incoming event attribution stays separate from inherited opening authorship; watch notifications are System-authored and retain the original source actor.

Paths and commands below are relative to the repository root. Read these invariants before editing this area; named code and tests hold implementation detail.

Membership departure clears matching Room reviewers and corner overrides atomically in the shared `membership-join.ts` removal primitives. Workspace and identity removal cover every affected Room; no replacement reviewer is inferred from a reused handle. The one-time `departed-reviewers-v1` backfill (`migrations/departed-reviewers.ts`) repairs earlier stale settings. Merge policy, including the zero-check commander's yes when no reviewer is configured, is unchanged. Coverage: `reviewer-membership.test.ts`.

A check-event wake or a same-head request sent before checks pass does not count as the first green-head review. `review_context.checks` retains dispatch-time checks; reviewer activity independently owns the displayed Review state. Green events request review unless the implementer is active or a real current-head request is queued. Historical verdicts never veto a later green event. A green handoff held by implementer activity stays owed in the machine until a real pending review request fulfills it; committed turn-end events and reconciliation dispatch that obligation without a timer or polling. Completed review turns with no approval or actionable findings do not retry or post chat notices. Each review wake carries the current head and brief revision plus the newest reviewer result or report. Orders to the configured reviewer use parent Room membership; reachable archived addresses report archived. Delivered findings retain their PR/head and are handed back once; a needed continuation includes prior reviewer text. A configured reviewer's explicit `report(done)` beginning with PASS records its verdict through `approveCornerMerge` after answer publication; that resource owner keeps the exact-head and approval checks.
Agent tags to the configured reviewer carry the current target and remain queued during an explicit wait. Answer publication ends the queue item through `agent-turn-end.ts`; failed diagnostic receipts alone cannot complete it. Current queued reviewer commands, pending checks and any active human hold suppress idle notices independently of the displayed oldest blocker. Attachment claims on reviewer verdicts and reports must have files in that review's delivery; both approval and the shared merge gate enforce this. Coverage: `corner-lifecycle-revision4.test.ts`, `corner-review-dispatch.test.ts`, `corner-review-dispatch-2.test.ts`, and `corner-attention.integration.test.ts`.

A failed head sends one implementer request after all checks finish, naming every failed job. Partial failures, later per-job failures and same-head reruns do not send extra repair requests. Provider freshness, current-head fences and lost-command recovery still apply. Coverage: `github-operations-6.test.ts` (AC-7 and CHECK-DEADLOCK-1), `corner-lifecycle-2.test.ts`.

Review wake decisions refresh a stored green from GitHub before planning a handoff. Provider-backed check commits carry live mergeability into the same transition; pending registration, including an empty rollup, cannot retain a cached green. Verified GitHub events and explicit helper commands retain their exact-corner head checks; a missing webhook requires explicit reconciliation. Committed fact changes, startup and listener resync recover recorded work without a repair timer. Coverage: `corner-review-dispatch.test.ts` (lost wake, wait release, stale head and explicit command refresh).

GitHub check refresh lifetime belongs to `GitHubOperations`: it tracks the whole webhook/check-read caller, including queued webhook admission and post-refresh queries, even after its caller disconnects. Shutdown first drains independent event jobs and closes HTTP/auth ingress, then awaits `stopCheckRefreshes()` on both foreground and jobs instances before closing pools. New work is refused once draining starts; existing errors still reject to their callers. Provider waits retain the existing shared request deadlines and return the first failure without a read-retry timer; no shutdown timeout may abandon a live database continuation. Coverage: `R-GH-SHUTDOWN` in `github-operations.test.ts`.

## Authority and lifecycle

- **Close uses current parent Room membership, independent of turn output.** Helper source context, completed commands and corner ancestry do not gate `archiveCorner`; the standing-corner lock remains explicit. `DaemonService.access` resolves membership through the parent even for archived targets, and close rechecks target reach under the archival authority lock before and after provider cleanup. The machine and installed-helper HTTP paths share this rule. Coverage: `corner-helper-close.test.ts` (completed owned turn, archived source, repeated close, person close and revoked membership).
- **Close and confirmed merge share one archive cleanup.** `archiveCorner` (`corner-lifecycle.ts`) transactionally cancels commands/working turns, removes pending attachments, archives the Room, abandons workflow runs, deletes wake sources and releases holds. Callers emit closed or merged events; the machine owns their archive cleanup. Locked standing corners keep their active work after a merge and do not enter archival. Stop cancels queued work in the same archival transaction; there are no claim or generation cleanup commands. The archive SQL sink is restricted to that machine effect by the architecture guard; close/merge cleanup regressions live in `corner-lifecycle.test.ts`.
- **MCP orders use the queue.** `selectMcpOrder` selects the named or oldest accessible pending order; its report completes it, and an unreported order stays pending. An explicit app call mints its own provenance-bearing `mcp_call` item without notifying a helper and completes it when the call returns. Coverage: `rooms-mcp.test.ts`.

- **The header and live checks read share the guarded check-summary writer.** A live read of the corner's recorded PR saves its nonempty provider snapshot through `refreshCheckRollup`, without another GitHub fetch; another PR, an old head or an older fetch cannot replace it. Completed `workflow_run` events also refresh the head, including reruns whose final check event did not update the summary. Committed `corner_github_cache` notifications deliver the result to phones. `CHECK-HEADER-1` in `github-operations.test.ts` covers the stale running count and read guards; `node --import tsx scripts/prove-corner-check-header.mjs` demonstrates signed webhook → built HTTP service → phone Room response → unchanged mobile header formatter, plus the live checks repair. Build the server first. This isolated provider-fixture proof does not claim a live Android/GitHub run.

- **The merge gate is one rule, PR/head-scoped and GitHub-authoritative:** `mergeAllowed = live checks green AND a yes on the exact head AND no hold`. `GitHubOperations.prChecksStatus` reads the live PR head's GraphQL `statusCheckRollup`; webhooks only trigger re-reads. Registered unfinished workflow runs, and check suites that already contain check runs, keep a head pending even when every existing context passed; both registration lists are paginated. A suite with zero check runs does not, unless a branch-protection required status check is still missing from the head. The required GitHub App must report that context; the same name from another app stays pending (`pr-checks-status.test.ts`, `github.test.ts`, EMPTY-SUITE-1). Pending check results change only after an actual webhook/head event or explicit check command; a lost completion webhook requires explicit operator reconciliation. Neither startup nor a minute timer scans pending or failed reads. Check-event wakes with a different head SHA are ignored under the lifecycle lock. Checks-read prose follows the live verdict, including pending registration with green contexts (`pr-checks-status.test.ts`, CHECK-HEAD-1). GitHub workflows that have not registered at all remain invisible to this read. Reopened PR webhooks re-read the live head and its check rollup; a green fact is scoped to head and attempt, so an old head cannot suppress the new review or leave its totals on the card (`github-operations.test.ts`, R1). The yes (`cornerMergeGate`, `apps/server/src/corner-lifecycle.ts`) is a configured reviewer agent's `approve_merge` PASS or a current Workspace owner or admin's yes (`record_merge_yes` or the phone's `approveCornerMerge`, both `recordPersonMergeYes`), or the recorded agent commander's `approve_merge` on a completed zero-check head with no reviewer (`isZeroCheckCommander`, `corner-merge-approval.ts`); all live in `corner_merge_approvals` (one row per corner). The server refuses a PASS from the current implementer or a PR commit author. Author checks read all PR commits from GitHub using Beeline git identities, fail closed on unavailable evidence, and recheck the live head before recording PASS. A new commit cancels the yes; a brief edit does not. A hold is the only veto. Yolo is not a merge condition. GitHub's live `dirty` mergeability blocks the gate. Merge-conflict wakes come only from a live mergeability read (`refreshStaleMergeability`); a stored verdict never wakes, and a new head resets it to unknown (`CONFLICT-LIVE-1` in `agent-command.integration-2.test.ts`). An explicit live checks read moves a stored head that missed its push webhook, and a failed provider read leaves the stored result unchanged (`CHECKS-LIVE-1` in `github-operations.test.ts`). `read(facet:checks,address)` returns facts only (`stage`, `checks`, `approved`, `held`, `mergeAllowed`), no prose rule. A provider-confirmed merged PR always reports `mergeAllowed: false`, including before archival. Archival is rechecked after provider reads. An archived corner reports `stage: closed` (or `merged` when GitHub confirms it) and `mergeAllowed: false`, even with passing checks and a current yes. `merge_corner` returns `blocked: the corner is closed` for a reachable archived corner, including one without a recorded PR; it does not hide the corner as missing. Coverage: `github-operations.test.ts` and `scripts/prove-closed-corner.mjs` (`CLOSED-1`).
- **Agent status exposes active merge holds.** `read(facet:status).verdict.holds` lists each open hold’s ID, holder ID/name and set time, including before a PR exists. `merge_corner` refusals include the same list and name blocking holds. Released holds are omitted; membership and release authority remain unchanged. Coverage: `read-only-mcp.open-corner.test.ts` and authenticated built-service proof `HOLD-IDS` in `corner-lifecycle.test.ts`.

- **Holds belong to their setter.** Agent hold paths retain the human requester for Room-access validation and record the agent separately. Agents release only their own holds, never person or other-agent holds. People with current Room access may release agent holds; person-to-person release still requires the holder or higher Workspace standing. Legacy rows remain person-set. Coverage: R8-HOLD in `corner-lifecycle.test.ts` and standing checks in `workspace-role-authority.test.ts`.

- **One merge path: `GitHubOperations.landCorner`.** A reviewer's PASS (`approveCornerMerge`, `daemon-service.ts`) and the phone's yes call it at once; a yes given while checks run wakes the implementer, whose `merge_corner` calls it once they pass; while the agent's record_merge_yes only records consent and merge_corner lands. It first refuses (`assertCornerBriefAllowsMerge`, `corner-brief.ts`, throwing `CornerBriefMergeRefusedError`) unless the corner's current brief assigns repository work: no brief revision, or `repositoryWork: false`, blocks landing through `merge_corner` and the phone's approve alike; recording a yes alone does not land (an unset `repositoryWork` is allowed; the reviewer's `approve_merge` PASS is still recorded). It then reads the gate live, rechecks local authority under the lifecycle lock (`confirmCornerMergeAuthority`: open corner, same head, repository-work brief, a yes on that head, no hold; nothing is stored) and squash-merges with the expected head; a refusal returns the corner to `implement`. GitHub merges a pull request at most once: a concurrent second attempt, or a lost response, reads the live pull request and confirms the merge instead of reporting a refusal; a confirmed unmerged head may be retried by any fresh gated request. No instruction may contain `gh pr merge`. A successful merge is confirmed against GitHub and archives the corner through the same idempotent path as the merge webhook. Actual merge webhooks and explicit check commands reconcile merges outside Beeline; a missed webhook awaits explicit reconciliation; there is no stored merge attempt, recovery back-off or unconfirmed-merge state. Reconciliation never calls the merge API. Coverage: `MERGE-LIVE` and AC-7 in `corner-lifecycle.test.ts`, and `background-shutdown.test.ts`.
- **Draft PRs remain blocked in live merge-readiness reads** (`blockedReason: PR is a draft`). On a green current-head reviewer PASS with no hold, `landCornerOutcome` marks the live matching PR ready using the repository App token, then re-reads checks and the gate before merging. A ready-mark failure persists a head-scoped marker and uses `reconcileCornerMergeBlockers` to report once to the commander; it never creates another timer. Drafts without reviewer PASS stay drafts. Coverage: `PR-2960-draft` in `corner-lifecycle.test.ts`, `github.test.ts`, and `read-only-mcp.pr-checks.test.ts`.

- **Merge queues preserve the same gate.** `GitHubAppClient.mergePullRequest` reads the base branch's GitHub merge queue and uses `enqueuePullRequest` with `expectedHeadOid` when configured; otherwise it keeps the squash REST path. A queued result is not a merge. `lifecycle.mergeQueue` drives the corner's queued status; explicit check commands and webhook reconciliation confirm merges through the existing archival path, dequeue on a hold or withdrawn approval, and return removed entries to implementation once with the combined commit's failing check names. A hold, a withdrawn yes or a merge attempt reads the corner's queue entry live (`reconcileQueuedCorners`), so an enqueue whose response was lost is still dequeued when the gate closes. Checks runs every required job on `merge_group` (`scripts/ci-release-contract.test.mjs`). The main ruleset keeps the required check names, squash merging and build concurrency of three. Activation and a real merge-group run remain operational proof, not something a local provider fixture can establish. Coverage: `corner-lifecycle.test.ts` (R1), `github.test.ts`.
- **Corner restart storms are bounded at both boundaries.** Restore reads use committed corner facts without GitHub; `featureBranch` and `lifecycle.branch` derive from the corner ID, and `closeRequested` derives from `rooms.archived_at IS NOT NULL`. `GitHubAppClient` coalesces exact-scope token grants and bounds requests; `github_installations.api_retry_at` shares installation cooldowns across replicas. Review handoffs/claims and merge gates still require fresh provider evidence and fail closed during a cooldown. Explicit reviewer failures end and report once; connection changes never reconstruct review work or clear a recovery marker. `WAKE-STORM` tests in `github-rate-limit.test.ts`, `github-operations.test.ts`, `corner-review-dispatch.test.ts` and `agent-turn-lifecycle.test.ts` cover the incident. Evidence and request counts: [2026-10-27 incident](corner-restart-storm-2026-10-27.md).

- **GitHub check-read rate limits return to the caller.** `GitHubHttpError` preserves `retry-after` or a primary reset with zero remaining budget. A documented 403 rate limit leaves checks pending and is excluded from Sentry capture; a plain 403 remains an error. Retry metadata does not schedule work. A later webhook or explicit check command supplies new admission; failed reads create no durable retry queue. REST check-read refusals retain the endpoint, bounded GitHub message, request ID and accepted-permissions header (SENTRY-1D in `github.test.ts` and `pr-checks-status.test.ts`); malformed error bodies retain status and retry classification. Live merge reads still fail closed. Coverage: `github.test.ts`, `github-operations.test.ts` (`R-GH-403`) and the real SDK collector in `sentry.test.ts`.
- **Corner reviewers use `corner_facts.reviewer_agent_id` when set, otherwise the parent Room reviewer** (`rooms.reviewer_agent_id`), only while that agent is a current member of the parent Room (`cornerReviewerSql`). Tags, review wakes, PASS, the checks read and the merge gate read this one list; there is no separate reachability check. A Room has one reviewer: fallback reviewer lists are deleted, a stored list is ignored, and `updateRoom` ignores `reviewerFallbackIds` from older phones (`FALLBACK-GONE` in `corner-reviewer-list.test.ts`). Any member agent may set the override with `reviewer` on `open_corner` or `revise_corner`; metadata changes need no brief revision. Setting it refuses the implementer and PR commit authors, clears prior agent approvals, and posts one corner line. Room reviewer settings remain person-owned. Reviewer dispatch excludes the current implementer; when that leaves no candidate it uses the existing missing/blocked-review handback, without adding an approval gate. `approveCornerMerge` (`daemon-service.ts`, refusals as `CornerVerdictRejectedError` in `corner-merge-approval.ts`) accepts a configured reviewer's current-head PASS. Without a reviewer, a completed zero-check head enters Review and hands the missing review back and privately wakes its implementer to ask its commander for a yes using the normal report tool (`noteMissingReviewer`); the server never posts a merge-decision message to a person in this flow. Other green heads wake the implementer to arrange review or report a merge decision to the commander. The green check fact queues a `corner_review_dispatch` command with review context; a `subscribed_event` check notice never counts as a review request. The head must be green as a whole; a passed job alongside queued checks does not dispatch review. Committed corner events and startup reconcile recorded facts, skipping pending or claimed implementer commands; head-scoped dispatch and report keys keep repeats quiet (`REVIEW-DISPATCH-BOUNDARY` in `github-operations.test.ts`). Green review gaps use `noteReviewBlocked` (`corner-lifecycle.ts`) to privately wake the implementer and report to the commander; coverage: `corner-lifecycle.test.ts` and `corner-reviewer-list.test.ts`.
- **Review source reads are assignment-scoped.** During a pending or claimed current-head review command, `getRoomMessage` from the corner can read the latest brief's approval/source and stored Intent message IDs in its source Room, within the same Workspace. An active current-head review also lends direct `getRoomConversation` and `getRoomMessage` reads in that exact source Room, including an approval DM; this creates no membership and grants no inbox, write or neighboring-Room access. Repair commands and verdict reports do not lend transcript access. Completed/cancelled reviews, archived corners and superseded heads or briefs lose this exception. Coverage: `corner-review-dispatch.test.ts` (`REVIEW-SOURCE-1`, `REVIEW-SOURCE-2`).
- **Review dispatch records its target** (`agent_commands.review_context`, `corner-lifecycle.ts`): PR number, head, brief revision and check results travel as context. A pending request deduplicates the same automatic event; historical completions do not veto a later request. Delivery, orders and reports never refresh GitHub or cancel an item for a changed head. Merge votes and provider operations retain their own current-head authority. Coverage: `corner-review-dispatch.test.ts`, `commander-order-target.integration.test.ts` and `github-operations.test.ts`.
- **Stale wake drops are measurable at delivery and claim.** `agent-command.ts` emits one structured `wake_dropped_stale` line with kind and recorded/current cause when it cancels a stale PR, brief or workflow wake. Brief assignment commands persist their revision in `wake_context`; distinct revisions with equal timestamps are fenced only after a current replacement command exists. Legacy wakes retain their existing fences. Cached-claim refusals commit stale cancellations before returning the error, so retries do not count the same cancellation twice. Cause-free traffic keeps its existing delivery rules. Experiment rollback is one revert; the additive nullable column may remain unused. Coverage: STALE-CAUSE-1 in `corner-review-dispatch.test.ts`; built HTTP proof: `node --import tsx scripts/prove-stale-wake-drop.mjs` after building the server. This isolated proof does not claim a production release.
- **One corner machine:** `transitionCorner` and `advanceCorner` in `corner-lifecycle.ts` own all state transitions and automatic wakes. `corner_facts.machine` replaces hidden lifecycle cards; old cards remain inert history for the expand release. Committed command/receipt, GitHub, wait and hold events, startup and listener resync enter the same runtime with no provider re-read or timer. The generic command queue retains work authority. The AST/SQL boundary in `scripts/corner-machine-boundary.mjs` runs in TYPECHECK and has a planted-violation test. See [state reference](corner-state-reference.md) and `corner-machine.test.ts`.
- **Explicit worker waits derive from the report log.** `cornerWaitingReportSql` selects the newest `blocked:`/`needs-decision:` worker report and its commander/tagged human audience; `waitingAnswered` on the report command/message records an answer. Private reports use their existing explicit report card to distinguish them from automatic final prose. Human replies in the corner or return Room and commander orders into the corner clear the wait; pushes and new PR heads preserve it. Report creation preserves other pending requests. Coverage: `REPORT-WAITING-DERIVED` in `corner-attention.integration.test.ts` and `corner-waiting-reason.test.ts`.
- **Corner state reads render the machine:** `working|review|waiting|idle|archived`; Review includes checks and reviewer work. Explicit blocked reports, questions and user actions remain Waiting during work and CI. Merge holds still veto only landing and allow implementation to continue. Phone and daemon rows read the same stored state. Coverage: `corner-state.test.ts`, `corner-state.exhaustive.test.ts`, `corner-state-reference.test.ts` and `corner-attention.integration.test.ts`.
- **Corner attention is event driven** (`corner-attention.ts`, `corner-attention.integration.test.ts`). Turn/report/hold/CI changes recompute the corner. When a turn ends with no pending work or explicit wait, its current commander receives one immediate idle signal. There is no post-turn grace timer or automatic-report budget. Pending CI, live work, future schedules and explicit holds suppress idle signals. Once dispatched, an idle notice is an ordinary queued input and stays owed until answered or stopped. Deterministic report IDs preserve one notice per episode across instances; commander turns do not create another episode. Other real source events can change that episode. The helper receives waiting inputs together, retaining their separate request IDs and results; connection hand-back is owned by the machine connection.
- **Startup failures do not start retry work.** A failed receipt records its outcome. No shared failure counter, automatic pause, cooldown DM or later timer re-admits it; a new command or connection lifecycle event owns the next attempt.

- **Room opening rows are historical.** Agent and human openings each leave one static `corner-open` row at their original position, including DM requests and scratch openings. The Room card contains no private origin or objective; off-Room call-site markers retain their existing settlement behavior. `GitHubOperations.processRepositoryEvent` publishes corner PR events with a server-resolved `cornerId`; direct landing and merge recovery reuse that event id. Phone and desktop PR rows open that corner. `visibleMessageSql` (`read-cursor.ts`) hides legacy Room completion-tip cards consistently across transcript/history/live reads, previews and unread counts; original opening markers that older servers settled project as Opened. There is no backfill for missing openings. Coverage: `corner-callsite.integration.test.ts` (`CORNER-ROOM-2`), `github-operations.test.ts`, and `corner-room-pr.browser.test.ts` (service snapshots supplied through `CORNER_ROOM_PROOF_INPUT`).

- **Corner goals can be kept current with `rename_corner` and its `objective` field**, including agent-opened corners. Lists and inspect reads take the objective from the latest brief revision, or the opening order's private payload when no brief exists. Goal edits update that location in place without a revision or wake; goal/title edits never rewrite System messages or cards. This changes navigation, not the approved brief or work scope. Coverage: `commander.integration.test.ts`.
- **A repository corner starts from a brief authorized by the dispatching message, never its short objective.** Brief = Markdown spec (≤ `CORNER_BRIEF_SPEC_MAX_LENGTH`) + file manifest + optional human message or active private commander order resolved server-side; without either, opening records the opening agent as agent-initiated (`resolveCornerBriefApproval`, `corner-brief.ts`). The objective is navigation only; the approval quote wins conflicts.
- **Any human in the Room can direct an agent and approve brief revisions**, including in a DM shared with the reviser (`corner-brief.ts`). The current corner commander (`cornerCommanderIdSql`) may revise directly without a citation; `commander-direct` records that agent as approver and cannot be reused by other agents. Human approvals require current membership in the corner's Room or the related message's Room. A newer conflicting human instruction wins; the agent revises the brief citing that message and states in the corner what changed. Opening needs no human approval. Revisions accept the parent Room’s human messages and active private orders addressed to the reviser from the corner’s recorded commander; a transcript order card resolves to its server-derived command identity. Completed/cancelled orders and agent-authored Room messages cannot approve revisions, including reuse of a stored order approval. Coverage: `commander.integration.test.ts` (`HUMAN-01`).
- **The brief's spec is the scope source.** `beeline-spec` (`apps/body/src/beeline-skill.ts`) writes intent, stories, criteria, non-goals, risks and references; `beeline-review` grades that outline. The dispatching message authorizes work; no separate spec/mock approval or Room post is required. Planning questions and mocks are agent judgment unless a person requests one before building (`CORNER_AUTHOR_CONTRACT`, `prompt-assembly.ts`). At each turn, the current brief replaces conflicting earlier delivered orders and review targets; prompt assembly labels older revision instructions as historical and binds the active reviewer target to the refreshed brief (`prompt-assembly.ts`; isolated R1/R2 in `corner-review-dispatch.test.ts`).
- **A corner is repository work exactly when its parent Room has a repository** (`rooms.repository_resolution='repository'` / `repository_key`); there is no `lane` column. A repository-backed corner, agent- or person-opened, opens on the code path directly (feature branch, PR, merge gate). A corner in a Room without a repository runs in `rooms/<corner>/scratch` with no token or checkout, never opens a pull request, and ends via human `requestCornerClose` or the `close_corner` of any agent that reaches it.
- **Orders use chat membership; reports use recorded return addresses.** `queueMessage` in `apps/server/src/agent-command.ts` selects a corner implementer, a named agent member, or the sole other agent at a Room/DM address. An ambiguous order returns “name which agent this order is for: @a, @b, @c” to its issuing agent, listing that Room’s agents; the agent then supplies a recipient. A member may order its own agent, another Room, a DM or an ancestor corner; there is no depth cap or reviewer-repair prerequisite. Brief revisions and lifecycle changes retain their separate authority. `order` and agent-directed `report` append private `agent_commands` items. Human reports enter the chat recorded with the original order; later context does not move it. Escalations follow the recorded opening or human-approved handover, one step at a time, with no recipient argument. An agent's final answer to a report wake uses that item's frozen return address. Identical reports from distinct items remain distinct; reconnect resends of one stored answer return its existing receipt. Explicit Stop/close refuses delivery through `wall('stop', reason)`; other pending work is never cancelled as stale. Report prose has no length cap, PR-read prerequisite or status admission gate; missing legacy status defaults to done, and an empty body cannot claim an answer. Turn activity, usage and lifecycle reconciliation run after commit without delaying the answer receipt. Coverage: `agent-queue.integration.test.ts`, `commander*.integration.test.ts`, `commander-wakes.integration.test.ts` and `agent-queue.postgres.test.ts`.
- **A corner has no membership: parent Room access is the authority, the branch is the shared artifact.** Only `agent_commands` authorize a turn (`agent-command.ts`); creation wakes the selected implementer only when it is a different agent from the opener; `room_access` projects corner access from current parent Room membership; corners have no `memberships` rows. `corner_person_state` stores explicit preferences lazily; keyed owed items and read marks stay in their existing sparse tables ([migration and reader audit](corner-membership-migration.md)). The agent uses its `workspace` tool and shell to prepare and synchronize its own checkout; checkout setup never precedes prompt delivery. Helpers receive work through the command socket and `server-command-intake.ts`. `DAEMON_OPERATION_ROUTES` must stay exhaustive.
- **A corner's worker is derived from its commands.** `cornerImplementerSql` (`corner-worker.ts`) is the agent of the latest assignment in the corner: the opening order (`corner_objective`) or a person's tag (`human_tag`), never the corner's reviewer; without one, the opener. A person tagging another agent assigns it the next CI, review and merge wakes; nobody is stopped and no release command is sent (`NO-SWAP` in `corner-lifecycle.test.ts`). Every agent works in its own checkout and the branch is the shared artifact. Agent tags in final replies and `post(address,text)` invite conversation in that place and assign nothing. Owed-history refresh follows only the ownership-defining assignment, not later tags (`corner_owed_opening_inserted`, `corner-owed.test.ts`), so ordinary tags do not rebuild that history per human member. The owner is derived too (`cornerOwnerSql`): the agent of the corner's earliest assignment, which is the opening order or, in a person-opened corner, the first agent a person tags there; nothing stores it; any current member agent may archive the corner (`archiveCorner` is membership-gated by `DaemonService.access`, like every other corner write).
- **GitHub's display cache has its own table.** `corner_github_cache.lifecycle` (PR, checks, mergeability) is written only by `github-operations.ts`, the helper remote-state functions in `corner-github-cache.ts` and the corner module's seed and close (rule `corner.github-cache-writes`); read it with `cornerLifecycleSql` or a `gh` join. `corner_facts` keeps `locked` and `reviewer_agent_id`, written only by the corner module (`corner.state-writes` total 0). Until a later `[drops data]` change drops `corner_facts.lifecycle`, a two-way trigger mirror (`CORNER_GITHUB_CACHE_MIRROR_SQL`) keeps older replicas correct.
- **People can lock a corner through its actions menu.** `corner_facts.locked` defaults false; `setCornerLocked` uses the same human permission as `requestCornerClose`. Agents cannot change the lock or close a locked corner. A confirmed merge records its result in history but keeps locked corners open, clears the merged PR from active lifecycle facts, returns the run to implement, preserves assignments and wake sources, and skips branch deletion. People can still close them, including after a merge. Coverage: `corner-lifecycle.test.ts` (`corner lock`) and `CornerActionsSheet.test.tsx` (the ⋯ sheet).
- **A phone closes a corner only through `PhoneService.requestCornerClose`** (current member; a human-created corner closes for its creator or a Workspace owner/admin), which applies `closeCornerState` (`corner-close.ts`); never close by chat prose. Every path that archives a corner — a human close, an agent's `close_corner` (`closeCornerState`), and the GitHub merge webhook (`GitHubOperations.mergeCorner`) — cancels its pending `agent_commands` and `working` turns in the same transaction via `cancelCornerAgentCommands`, so landing a corner never leaves a stale assignment behind. Closing and landing also abandon live saved workflows via `abandonCornerWorkflowRuns` (`workflow-runs.ts`; `corner-lifecycle.test.ts`). After archival commits, the caller makes one best-effort attempt to delete the corner's derived branch (`feature/corner-<first 12 hex characters of its ID without dashes>`), rechecking GitHub's live default/protection, open head/base PRs and all unarchived corners in that repository. Reserved and release branches stay; unmerged corners retain commits absent from the default branch. Failures are logged without blocking archival, with no branch queue or retry timer; missing refs (404/422) count as done. Explicit historical maintenance scans archived corners afresh and requires containment for every branch, allowing a squash-merge exception only when the live tip equals that corner's merged PR head; see [archived corner cleanup](archived-corner-cleanup.md). Explicit close checks authority, attempts to close the recorded unmerged PR through `GitHubOperations.closeCornerPullRequest` outside the archival transaction, then rechecks authority under the lifecycle lock and archives. GitHub failures are logged and never prevent archival (`closeCornerPullRequestBestEffort`, `corner-close.ts`); there is no retry queue, and `close_corner_pr` repairs a PR left open. PR closure rechecks that the branch is not the base of an open PR. Archival releases the corner's active merge holds in the same transaction (`releaseArchivedCornerHolds`, `corner-holds.ts`; `HOLD-ARCHIVE` in `corner-lifecycle.test.ts`); a locked corner that merges stays open and keeps its holds. Any agent that reaches a repository corner closes its PR without merging through `close_corner_pr(address)` (`GitHubOperations.closeCornerPullRequest`): the branch stays and `lifecycle.pr` is cleared so the merge gate reads no PR. This also repairs legacy archived corners without reopening them or waking work; merged corners are excluded.
