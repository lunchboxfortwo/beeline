# Corner authority and lifecycle invariants

`message(to:{agent,place},text,ask?)` records both endpoints and returns its id.
`reply(id,text,ask?)` returns to that sender in that place without selecting a commander.
The sender of the task message remains its commander across brief revisions and later tags.
System wakes continue that thread task and retain its commander's tuple as their reply destination.
That commander is the sender of the opening task, else of the first task delivered to the implementer; a tag of another agent never replaces it.
Thread work never takes a turn outside the thread: review gaps wake only the implementer there, and a commander who becomes the implementer gets no notice elsewhere.
A closed return place ends the turn without rerouting.
Each ask owns its wait and, for a person, its own answer card with an automatic source link.
Plain text, including blocked or done wording, creates no card.
Attachments follow the same recorded tuple.
Coverage: `messaging-s1-implementer.test.ts` through `messaging-s8-idle.test.ts`; the owner's four conditions, including external MCP and joined-session agents, in `messaging-c1-reply-place.test.ts` through `messaging-c4-external.test.ts`.

Queued and in-flight legacy protocol items retain their stored routing through the compatibility adapter.
The single removal point is `messaging-cutover.ts`: delete its adapter and the old daemon routes together after the queue drains.
New tools advertise only messages and replies.

Paths and commands below are relative to the repository root. Read these invariants before editing this area; named code and tests hold implementation detail.

Membership departure clears matching Room reviewers and corner overrides atomically in the shared `membership-join.ts` removal primitives. Workspace and identity removal cover every affected Room; no replacement reviewer is inferred from a reused handle. The one-time `departed-reviewers-v1` backfill (`migrations/departed-reviewers.ts`) repairs earlier stale settings. With no current reviewer configured, the merge gate requires no approval. Coverage: `reviewer-membership.test.ts`.

A check-event wake or a same-head request sent before checks pass does not count as the first green-head review. `review_context.checks` retains dispatch-time checks; reviewer activity independently owns the displayed Review state. Green events request a configured reviewer unless the implementer is active or a real current-head request is queued. Historical verdicts never veto a later green event. A green handoff held by implementer activity stays owed in the machine until a real pending review request fulfills it; committed turn-end events and reconciliation dispatch that obligation without a timer or polling. Completed review turns with no approval or actionable findings do not retry or post chat notices. Each review wake carries the current head and brief revision plus the newest reviewer result or report. Orders to the configured reviewer use parent Room membership; reachable archived addresses report archived. Delivered findings retain their PR/head and are handed back once; a needed continuation includes prior reviewer text. A configured reviewer records its exact-head verdict with `approve_merge`; legacy report verdicts remain readable only through the cutover window.
Agent tags to the configured reviewer carry the current target and remain queued during an explicit wait. Answer publication ends the queue item through `agent-turn-end.ts`; failed diagnostic receipts alone cannot complete it. Current queued reviewer commands, pending checks and any active human hold suppress idle notices independently of the displayed oldest blocker. Coverage: `corner-lifecycle-revision4.test.ts`, `corner-review-dispatch.test.ts`, `corner-review-dispatch-2.test.ts`, and `corner-attention.integration.test.ts`.

A failed head sends one implementer request after all checks finish, naming every failed job. Partial failures, later per-job failures and same-head reruns do not send extra repair requests. Provider freshness, current-head fences and lost-command recovery still apply. Coverage: `github-operations-6.test.ts` (AC-7 and CHECK-DEADLOCK-1), `corner-lifecycle-2.test.ts`.

Review wake decisions refresh a stored green from GitHub before planning a handoff. Provider-backed check commits carry live mergeability into the same transition; pending registration, including an empty rollup, cannot retain a cached green. Verified GitHub events and explicit helper commands retain their exact-corner head checks; a missing webhook requires explicit reconciliation. Committed fact changes, startup and listener resync recover recorded work without a repair timer. Coverage: `corner-review-dispatch.test.ts` (lost wake, wait release, stale head and explicit command refresh).

GitHub check refresh lifetime belongs to `GitHubOperations`: it tracks the whole webhook/check-read caller, including queued webhook admission and post-refresh queries, even after its caller disconnects. Shutdown first drains independent event jobs and closes HTTP/auth ingress, then awaits `stopCheckRefreshes()` on both foreground and jobs instances before closing pools. New work is refused once draining starts; existing errors still reject to their callers. Provider waits retain the existing shared request deadlines and return the first failure without a read-retry timer; no shutdown timeout may abandon a live database continuation. Coverage: `R-GH-SHUTDOWN` in `github-operations.test.ts`.

## Authority and lifecycle

- **Close uses current parent Room membership, independent of turn output.** Helper source context, completed commands and corner ancestry do not gate `archiveCorner`; the standing-corner lock remains explicit. `DaemonService.access` resolves membership through the parent even for archived targets, and close rechecks target reach under the archival authority lock before and after provider cleanup. The machine and installed-helper HTTP paths share this rule. Coverage: `corner-helper-close.test.ts` (completed owned turn, archived source, repeated close, person close and revoked membership).
- **Close and confirmed merge share one archive cleanup.** `archiveCorner` (`corner-lifecycle.ts`) transactionally cancels commands/working turns, removes pending attachments, archives the Room, abandons workflow runs, deletes wake sources and releases holds. Callers emit closed or merged events; the machine owns their archive cleanup. Locked standing corners keep their active work after a merge and do not enter archival. Stop cancels queued work in the same archival transaction; there are no claim or generation cleanup commands. The archive SQL sink is restricted to that machine effect by the architecture guard; close/merge cleanup regressions live in `corner-lifecycle.test.ts`.
- **MCP messages use the queue.** A message id selects its received item; replying completes it, and an unanswered task stays pending. An explicit app call mints its own provenance-bearing `mcp_call` item without notifying a helper and completes it when the call returns. Coverage: `rooms-mcp.test.ts`.

- **The header and live checks read share the guarded check-summary writer.** A live read of the corner's recorded PR saves its nonempty provider snapshot through `refreshCheckRollup`, without another GitHub fetch; another PR, an old head or an older fetch cannot replace it. Completed `workflow_run` events also refresh the head, including reruns whose final check event did not update the summary. Committed `corner_github_cache` notifications deliver the result to phones. `CHECK-HEADER-1` in `github-operations.test.ts` covers the stale running count and read guards; `node --import tsx scripts/prove-corner-check-header.mjs` demonstrates signed webhook → built HTTP service → phone Room response → unchanged mobile header formatter, plus the live checks repair. Build the server first. This isolated provider-fixture proof does not claim a live Android/GitHub run.

- **The merge gate is one rule, PR/head-scoped and GitHub-authoritative:** `mergeAllowed = PR not merged AND corner open AND live checks green AND a configured reviewer (not implementer) PASS on the exact head when a reviewer is configured AND no hold AND merge target matches the linked repository`. `GitHubOperations.prChecksStatus` reads the live PR head's GraphQL `statusCheckRollup`; webhooks only trigger re-reads. Registered unfinished workflow runs, and check suites that already contain check runs, keep a head pending even when every existing context passed; both registration lists are paginated. A suite with zero check runs does not, unless a branch-protection required status check is still missing from the head. The required GitHub App must report that context; the same name from another app stays pending (`pr-checks-status.test.ts`, `github.test.ts`, EMPTY-SUITE-1). Pending check results change only after an actual webhook/head event or explicit check command; a lost completion webhook requires explicit operator reconciliation. Neither startup nor a minute timer scans pending or failed reads. Check-event wakes with a different head SHA are ignored under the lifecycle lock. Checks-read prose follows the live verdict, including pending registration with green contexts (`pr-checks-status.test.ts`, CHECK-HEAD-1). GitHub workflows that have not registered at all remain invisible to this read. Reopened PR webhooks re-read the live head and its check rollup; a green fact is scoped to head and attempt, so an old head cannot suppress the new review or leave its totals on the card (`github-operations.test.ts`, R1). A configured reviewer's `approve_merge` PASS is stored in `corner_merge_approvals` (one row per corner). With no reviewer configured, no approval is needed; people control merging through holds. The server refuses a PASS from the current implementer or a PR commit author. Author checks read all PR commits from GitHub using Beeline git identities, fail closed on unavailable evidence, and recheck the live head before recording PASS. A new commit cancels the yes; a brief edit does not. A hold is the only veto. Yolo is not a merge condition. Merge-conflict wakes come only from a live mergeability read (`refreshStaleMergeability`); a stored verdict never wakes, and a new head resets it to unknown (`CONFLICT-LIVE-1` in `agent-command.integration-2.test.ts`). An explicit live checks read moves a stored head that missed its push webhook, and a failed provider read leaves the stored result unchanged (`CHECKS-LIVE-1` in `github-operations.test.ts`). `read(facet:checks,address)` returns facts only (`stage`, `checks`, `approved`, `held`, `mergeAllowed`), no prose rule. A provider-confirmed merged PR always reports `mergeAllowed: false`, including before archival. Archival is rechecked after provider reads. An archived corner reports `stage: closed` (or `merged` when GitHub confirms it) and `mergeAllowed: false`, even with passing checks and a current yes. Coverage: `github-operations.test.ts`.
- **Agent status exposes active merge holds.** `read(facet:status).verdict.holds` lists each open hold’s ID, holder ID/name and set time, including before a PR exists. Released holds are omitted; membership and release authority remain unchanged. Coverage: `read-only-mcp.open-corner.test.ts` and authenticated built-service proof `HOLD-IDS` in `corner-lifecycle.test.ts`.

- **Holds belong to their setter.** Agent hold paths retain the human requester for Room-access validation and record the agent separately. Agents release only their own holds, never person or other-agent holds. People with current Room access may release agent holds; person-to-person release still requires the holder or higher Workspace standing. Legacy rows remain person-set. Coverage: R8-HOLD in `corner-lifecycle.test.ts` and standing checks in `workspace-role-authority.test.ts`.

- **One merge path: `GitHubOperations.landCorner`.** The server lands after a reviewer PASS, green checks, or a hold release opens the six-condition gate. The existing head-scoped `land` effect receipt claims the automatic attempt under the lifecycle lock; it never wakes an implementer. The merge uses GitHub's expected head. A successful live confirmation or merge webhook archives through the same idempotent path; a provider refusal returns its reason. There is no polling, timer or automatic retry. `scripts/check-walls.mjs` fixes the six conditions and allowed corner states; changing those lists requires owner approval. Coverage: `corner-server-merge.test.ts`, `MERGE-LIVE` and AC-7 in `corner-lifecycle.test.ts`.

- **Merge queues preserve the same gate.** `GitHubAppClient.mergePullRequest` reads the base branch's GitHub merge queue and uses `enqueuePullRequest` with `expectedHeadOid` when configured; otherwise it keeps the squash REST path. A queued result is not a merge. `lifecycle.mergeQueue` drives the corner's queued status; explicit check commands and webhook reconciliation confirm merges through the existing archival path, dequeue on a hold or withdrawn approval, and return removed entries to implementation once with the combined commit's failing check names. A hold, a withdrawn yes or a merge attempt reads the corner's queue entry live (`reconcileQueuedCorners`), so an enqueue whose response was lost is still dequeued when the gate closes. Checks runs every required job on `merge_group` (`scripts/ci-release-contract.test.mjs`). The main ruleset keeps the required check names, squash merging and build concurrency of three. Activation and a real merge-group run remain operational proof, not something a local provider fixture can establish. Coverage: `corner-lifecycle.test.ts` (R1), `github.test.ts`.
- **Corner restart storms are bounded at both boundaries.** Restore reads use committed corner facts without GitHub; `featureBranch` and `lifecycle.branch` derive from the corner ID, and `closeRequested` derives from `rooms.archived_at IS NOT NULL`. `GitHubAppClient` coalesces exact-scope token grants and bounds requests; `github_installations.api_retry_at` shares installation cooldowns across replicas. Review handoffs/claims and merge gates still require fresh provider evidence and fail closed during a cooldown. Explicit reviewer failures end and report once; connection changes never reconstruct review work or clear a recovery marker. `WAKE-STORM` tests in `github-rate-limit.test.ts`, `github-operations.test.ts`, `corner-review-dispatch.test.ts` and `agent-turn-lifecycle.test.ts` cover the incident. Evidence and request counts: [2026-10-27 incident](corner-restart-storm-2026-10-27.md).

- **GitHub check-read rate limits return to the caller.** `GitHubHttpError` preserves `retry-after` or a primary reset with zero remaining budget. A documented 403 rate limit leaves checks pending and is excluded from Sentry capture; a plain 403 remains an error. Retry metadata does not schedule work. A later webhook or explicit check command supplies new admission; failed reads create no durable retry queue. REST check-read refusals retain the endpoint, bounded GitHub message, request ID and accepted-permissions header (SENTRY-1D in `github.test.ts` and `pr-checks-status.test.ts`); malformed error bodies retain status and retry classification. Live merge reads still fail closed. Coverage: `github.test.ts`, `github-operations.test.ts` (`R-GH-403`) and the real SDK collector in `sentry.test.ts`.
- **Corner reviewers use `corner_facts.reviewer_agent_id` when set, otherwise the parent Room reviewer** (`rooms.reviewer_agent_id`), only while that agent is a current member of the parent Room (`cornerReviewerSql`). Tags, review wakes, PASS, the checks read and the merge gate read this one list; there is no separate reachability check. A Room has one reviewer: fallback reviewer lists are deleted, a stored list is ignored, and `updateRoom` ignores `reviewerFallbackIds` from older phones (`FALLBACK-GONE` in `corner-reviewer-list.test.ts`). Any member agent may set the override with `reviewer` on `open_thread` or `revise_thread`; metadata changes need no brief revision. Setting it refuses the implementer and PR commit authors, clears prior agent approvals, and posts one corner line. Room reviewer settings remain person-owned. Reviewer dispatch excludes the current implementer; when that leaves no candidate it uses the existing missing/blocked-review handback, without adding an approval gate. `approveCornerMerge` (`daemon-service.ts`, refusals as `CornerVerdictRejectedError` in `corner-merge-approval.ts`) accepts a configured reviewer's current-head PASS. With no reviewer configured, no approval or implementer handback is needed. A configured reviewer that is also the implementer still needs independent review through the existing handback. The green check fact queues a `corner_review_dispatch` command with review context; a `subscribed_event` check notice never counts as a review request. The head must be green as a whole; a passed job alongside queued checks does not dispatch review. Committed corner events and startup reconcile recorded facts, skipping pending or claimed implementer commands; head-scoped dispatch and report keys keep repeats quiet (`REVIEW-DISPATCH-BOUNDARY` in `github-operations.test.ts`). Green review gaps use `noteReviewBlocked` (`corner-lifecycle.ts`) to privately wake the implementer in the thread, which replies with the blocker to its commander; coverage: `corner-lifecycle.test.ts` and `corner-reviewer-list.test.ts`.
- **Review source reads are assignment-scoped.** During a pending or claimed current-head review command, `getRoomMessage` from the corner can read the latest brief's approval/source and stored Intent message IDs in its source Room, within the same Workspace. An active current-head review also lends direct `getRoomConversation` and `getRoomMessage` reads in that exact source Room, including an approval DM; this creates no membership and grants no inbox, write or neighboring-Room access. Repair commands and verdict reports do not lend transcript access. Completed/cancelled reviews, archived corners and superseded heads or briefs lose this exception. Coverage: `corner-review-dispatch.test.ts` (`REVIEW-SOURCE-1`, `REVIEW-SOURCE-2`).
- **Review dispatch records its target** (`agent_commands.review_context`, `corner-lifecycle.ts`): PR number, head, brief revision and check results travel as context. A pending request deduplicates the same automatic event; historical completions do not veto a later request. Delivery, orders and reports never refresh GitHub or cancel an item for a changed head. Merge votes and provider operations retain their own current-head authority. Coverage: `corner-review-dispatch.test.ts`, `commander-order-target.integration.test.ts` and `github-operations.test.ts`.
- **Stale wake drops are measurable at delivery and claim.** `agent-command.ts` emits one structured `wake_dropped_stale` line with kind and recorded/current cause when it cancels a stale PR, brief or workflow wake. Brief assignment commands persist their revision in `wake_context`; distinct revisions with equal timestamps are fenced only after a current replacement command exists. Legacy wakes retain their existing fences. Cached-claim refusals commit stale cancellations before returning the error, so retries do not count the same cancellation twice. Cause-free traffic keeps its existing delivery rules. Experiment rollback is one revert; the additive nullable column may remain unused. Coverage: STALE-CAUSE-1 in `corner-review-dispatch.test.ts`; built HTTP proof: `node --import tsx scripts/prove-stale-wake-drop.mjs` after building the server. This isolated proof does not claim a production release.
- **One corner machine:** `transitionCorner` and `advanceCorner` in `corner-lifecycle.ts` own all state transitions and automatic wakes. `corner_facts.machine` replaces hidden lifecycle cards; old cards remain inert history for the expand release. Committed command/receipt, GitHub, wait and hold events, startup and listener resync enter the same runtime with no provider re-read or timer. The generic command queue retains work authority. The AST/SQL boundary in `scripts/corner-machine-boundary.mjs` runs in TYPECHECK and has a planted-violation test. See [state reference](corner-state-reference.md) and `corner-machine.test.ts`.
- **Explicit worker blocks derive from report status.** The authenticated `report` operation stores `reportStatus` on its private command or human-directed message. `cornerWaitingReportSql` uses that marker, with optional legacy card linkage; ordinary final prose creates no block. Each recipient’s wait clears when that recipient posts a later non-System message in the corner or replies on the report’s thread; other people’s messages, orders and wakes do not clear it. The implementer’s later explicit `done`/`failed` report, a granted-command activity row in the corner, or a new implementer-authored ask card still lifts the block for every recipient. The new card retains its native pending state. Coverage: `corner-worker-block.integration.test.ts`, `corner-waiting-reason.test.ts` and the real report path in `commander.integration.test.ts`.
- **Corner state reads render the machine:** `working|review|waiting|idle|archived`; Review includes checks and reviewer work. Explicit blocked reports, questions and user actions remain Waiting during work and CI. Merge holds still veto only landing and allow implementation to continue. Phone and daemon rows read the same stored state. Coverage: `corner-state.test.ts`, `corner-state.exhaustive.test.ts`, `corner-state-reference.test.ts` and `corner-attention.integration.test.ts`.
- **Corner attention is event driven** (`corner-attention.ts`). Committed work, native requests, decisions, reports, holds and CI recompute the corner. Idle notices have a budget of one per corner since the latest person event, derived from report history: a human message in or addressed to the corner, a human card/grant decision, or a human hold release. Agent/System reactions and worker output never replenish it. An outstanding idle notice retains its slot; deterministic IDs and the corner transaction serialize delivery across instances. Spent corners remain visibly Idle without more agent work. Pending CI, live implementer/reviewer work, future schedules and holds suppress notices. Roles come from assignments and dispatch context, never creator identity. Freshness still discards obsolete notices. Coverage: `corner-worker-block.integration.test.ts` and `corner-attention.integration.test.ts`.
- **Startup failures do not start retry work.** A failed receipt records its outcome. No shared failure counter, automatic pause, cooldown DM or later timer re-admits it; a new command or connection lifecycle event owns the next attempt.

- **Room opening rows are historical.** Agent and human openings each leave one static `corner-open` row at their original position, including DM requests and scratch openings. The Room card contains no private origin or objective; off-Room call-site markers retain their existing settlement behavior. `GitHubOperations.processRepositoryEvent` publishes corner PR events with a server-resolved `cornerId`; direct landing and merge recovery reuse that event id. Phone and desktop PR rows open that corner. `visibleMessageSql` (`read-cursor.ts`) hides legacy Room completion-tip cards consistently across transcript/history/live reads, previews and unread counts; original opening markers that older servers settled project as Opened. There is no backfill for missing openings. Coverage: `corner-callsite.integration.test.ts` (`CORNER-ROOM-2`), `github-operations.test.ts`, and `corner-room-pr.browser.test.ts` (service snapshots supplied through `CORNER_ROOM_PROOF_INPUT`).

- **Corner goals can be kept current with `rename_thread` and its `objective` field**, including agent-opened corners. Lists and inspect reads take the objective from the latest brief revision, or the opening order's private payload when no brief exists. Goal edits update that location in place without a revision or wake; goal/title edits never rewrite System messages or cards. This changes navigation, not the approved brief or work scope. Coverage: `commander.integration.test.ts`.
- **A repository corner starts from a brief authorized by the dispatching message, never its short objective.** Brief = Markdown spec (≤ `CORNER_BRIEF_SPEC_MAX_LENGTH`) + file manifest + optional human message or active private commander order resolved server-side; without either, opening records the opening agent as agent-initiated (`resolveCornerBriefApproval`, `corner-brief.ts`). The objective is navigation only; the approval quote wins conflicts.
- **Any human in the Room can direct an agent and approve brief revisions**, including in a DM shared with the reviser (`corner-brief.ts`). The current corner commander (`cornerCommanderIdSql`) may revise directly without a citation; `commander-direct` records that agent as approver and cannot be reused by other agents. Human approvals require current membership in the corner's Room or the related message's Room. A newer conflicting human instruction wins; the agent revises the brief citing that message and states in the corner what changed. Opening needs no human approval. Revisions accept the parent Room’s human messages and active private orders addressed to the reviser from the corner’s recorded commander; a transcript order card resolves to its server-derived command identity. Completed/cancelled orders and agent-authored Room messages cannot approve revisions, including reuse of a stored order approval. Coverage: `commander.integration.test.ts` (`HUMAN-01`).
- **The brief's spec is the scope source.** `beeline-spec` (`apps/body/src/beeline-skill.ts`) writes intent, stories, criteria, non-goals, risks and references; `beeline-review` grades that outline. The dispatching message authorizes work; no separate spec/mock approval or Room post is required. Planning questions and mocks are agent judgment unless a person requests one before building (`CORNER_AUTHOR_CONTRACT`, `prompt-assembly.ts`). At each turn, the current brief replaces conflicting earlier delivered orders and review targets; prompt assembly labels older revision instructions as historical and binds the active reviewer target to the refreshed brief (`prompt-assembly.ts`; isolated R1/R2 in `corner-review-dispatch.test.ts`).
- **A corner is repository work exactly when its parent Room has a repository** (`rooms.repository_resolution='repository'` / `repository_key`); there is no `lane` column. A repository-backed corner, agent- or person-opened, opens on the code path directly (feature branch, PR, merge gate). A corner in a Room without a repository runs in `rooms/<corner>/scratch` with no token or checkout, never opens a pull request, and ends via human `requestCornerClose` or the `close_thread` of any agent that reaches it.
- **Publication and completion commit together.** `answerQueuedMessage` publishes through `sendMessage` before the terminal writer completes its received item.
  Optional activity and lifecycle reconciliation follow publication without delaying its receipt.
  Reconnect delivery of a completed item returns its recorded receipt.
  Legacy status/ask handling lives only for the cutover window described above.
- **A corner has no membership: parent Room access is the authority, the branch is the shared artifact.** Only `agent_commands` authorize a turn (`agent-command.ts`); creation wakes the selected implementer only when it is a different agent from the opener; `room_access` projects corner access from current parent Room membership; corners have no `memberships` rows. `corner_person_state` stores explicit preferences lazily; keyed owed items and read marks stay in their existing sparse tables ([migration and reader audit](corner-membership-migration.md)). The agent uses its `workspace` tool and shell to prepare and synchronize its own checkout; checkout setup never precedes prompt delivery. Helpers receive work through the command socket and `server-command-intake.ts`. `DAEMON_OPERATION_ROUTES` must stay exhaustive.
- **A thread's implementer is recorded.** `cornerImplementerSql` reads `corner_facts.implementer_agent_id`. The opening assignment initializes it; a human-opened thread uses its first person tag, following `cornerOwnerSql`. Later tags never transfer the role. Only `claim_thread` changes it. Agent pushes and PR opens require the recorded implementer. Deleting an identity clears its recorded implementer reference. Existing threads are backfilled once from the previous latest-assignment derivation. Coverage: `thread-implementer.test.ts`. The owner is derived too (`cornerOwnerSql`): the agent of the corner's earliest assignment, which is the opening order or, in a person-opened corner, the first agent a person tags there; nothing stores it; any current member agent may archive the corner (`archiveCorner` is membership-gated by `DaemonService.access`, like every other corner write).
- **GitHub's display cache has its own table.** `corner_github_cache.lifecycle` (PR, checks, mergeability) is written only by `github-operations.ts`, the helper remote-state functions in `corner-github-cache.ts` and the corner module's seed and close (rule `corner.github-cache-writes`); read it with `cornerLifecycleSql` or a `gh` join. `corner_facts` keeps `locked`, `reviewer_agent_id` and `implementer_agent_id`, written only by the corner module (`corner.state-writes` total 0). Until a later `[drops data]` change drops `corner_facts.lifecycle`, a two-way trigger mirror (`CORNER_GITHUB_CACHE_MIRROR_SQL`) keeps older replicas correct.
- **People can lock a corner through its actions menu.** `corner_facts.locked` defaults false; `setCornerLocked` uses the same human permission as `requestCornerClose`. Agents cannot change the lock or close a locked corner. A confirmed merge records its result in history but keeps locked corners open, clears the merged PR from active lifecycle facts, returns the run to implement, preserves assignments and wake sources, and skips branch deletion. People can still close them, including after a merge. Coverage: `corner-lifecycle.test.ts` (`corner lock`) and `CornerActionsSheet.test.tsx` (the ⋯ sheet).
- **A phone closes a corner only through `PhoneService.requestCornerClose`** (current member; a human-created corner closes for its creator or a Workspace owner/admin), which applies `closeCornerState` (`corner-close.ts`); never close by chat prose. Every path that archives a corner — a human close, an agent's `close_thread` (`closeCornerState`), and the GitHub merge webhook (`GitHubOperations.mergeCorner`) — cancels its pending `agent_commands` and `working` turns in the same transaction via `cancelCornerAgentCommands`, so landing a corner never leaves a stale assignment behind. Closing and landing also abandon live saved workflows via `abandonCornerWorkflowRuns` (`workflow-runs.ts`; `corner-lifecycle.test.ts`). After archival commits, the caller makes one best-effort attempt to delete the corner's derived branch (`feature/corner-<first 12 hex characters of its ID without dashes>`), rechecking GitHub's live default/protection, open head/base PRs and all unarchived corners in that repository. Reserved and release branches stay; unmerged corners retain commits absent from the default branch. Failures are logged without blocking archival, with no branch queue or retry timer; missing refs (404/422) count as done. Explicit historical maintenance scans archived corners afresh and requires containment for every branch, allowing a squash-merge exception only when the live tip equals that corner's merged PR head; see [archived corner cleanup](archived-corner-cleanup.md). Explicit close checks authority, attempts to close the recorded unmerged PR through `GitHubOperations.closeCornerPullRequest` outside the archival transaction, then rechecks authority under the lifecycle lock and archives. GitHub failures are logged and never prevent archival (`closeCornerPullRequestBestEffort`, `corner-close.ts`); there is no retry queue, and `close_thread_pr` repairs a PR left open. PR closure rechecks that the branch is not the base of an open PR. Archival releases the corner's active merge holds in the same transaction (`releaseArchivedCornerHolds`, `corner-holds.ts`; `HOLD-ARCHIVE` in `corner-lifecycle.test.ts`); a locked corner that merges stays open and keeps its holds. Any agent that reaches a repository corner closes its PR without merging through `close_thread_pr(address)` (`GitHubOperations.closeCornerPullRequest`): the branch stays and `lifecycle.pr` is cleared so the merge gate reads no PR. This also repairs legacy archived corners without reopening them or waking work; merged corners are excluded.
- **An agent reaches a corner when it is a current member of its parent Room** (`DaemonService.reach`). Reach authorizes closing, renaming, ordering, revising the brief, reading (status, transcript, brief, checks, PR discussion, members) and corner posting via `post`. Room posting requires current membership in the addressed Room; omitted address uses the active corner. Check reach on the target `cornerId`, never only on the turn's `roomId`.
